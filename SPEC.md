## Current state

Arca is in phase 1: functional, with stabilization in progress. It consists of a Node 24 daemon that runs as a hub or a replica, a Docker image for servers, a Tauri desktop app (macOS Apple Silicon is the primary target; Windows and Linux installers are built and published), a web UI shared with the desktop, an Expo replica for Android and iOS phones and the Fold, a static website and an Umbrel package.

- **Pilot.** Casa (Docker hub), the maintainer's Mac (desktop replica), a Samsung Fold (mobile replica) and an Umbrel server hold real user data. Never reset their state, unlink shares or run destructive diagnostics to get a clean result; use isolated tests. A successful status or catalog request is not a completed synchronization: check each selected folder's completion time, content and errors.
- **Source is not deployment.** A commit changes none of the running daemons, apps or containers. Native mobile changes need a new binary, desktop changes a rebuilt app, daemon changes a restarted service, and Casa a user-managed redeploy. Which builds and deployments are pending lives in ROADMAP (BUILD-DESKTOP, P1-CASA-DEPLOY, CASA-VERSION).
- **Compatibility.** Desktop and server replicas refuse a hub without `directories`, `changes` and `pathTransitions`; phones refuse one without `directories` and `pathTransitions`, and without `blobRanges` for downloads; the hub answers 412 to sync clients missing the directory and path-transition headers. `gallery`, `galleryDeletion` and `music` only switch features off when absent. Deploy replicas and phones before or together with the hub, because a hub that knows a newer fixed exclusion list rejects proposals for those paths from older replicas.
- **Qualification.** Automated tests exercise sync, restart, conflicts, permissions and recovery in isolation. They do not certify native installations, physical devices, sustained load, power loss or an independent backup restore; those gates are ROADMAP `verify` tasks.
- **Where to start.** Read the section a task touches: [synchronization](#3-synchronization) for protocol and file safety, [desktop, server and web](#4-desktop-server-and-web) or [mobile](#5-mobile) for client behavior, [operations](#8-operations) for commands, Casa, releases and Umbrel, and the [design system](#9-design-system-and-interactions) for any UI change.

## 1. Product decisions

Arca synchronizes personal files across hardware owned by one person. It has its own daemon and protocol: no Syncthing, external account, public relay or telemetry.

- **One hub.** The user chooses one hub: a PC, Mac or server (Docker is a deployment option, not the definition of a hub). Only the hub creates shared folders, either adopting existing folders or creating new ones at independent paths. An empty hub can be linked before its first folder exists.
- **Replicas choose destinations.** Other machines select whole shared folders and choose an independent local destination for each. The folder ID identifies the share; its name and source path never dictate destination paths. Existing destination files take part in two-way sync. A replica can add, edit and delete files but never creates a share.
- **Complete copies.** Selected working copies stay complete on disk and available offline once downloaded: no placeholders and no on-demand eviction. Linking a mobile album adds photo-library uploads while the device keeps its complete copy.
- **Distinct operations.** Pause, Stop syncing on a device, Stop syncing here on the hub, hub Delete share, Disconnect, Remove device and Erase are different operations with the file and history consequences described in [Stop syncing, relink and unselection](#stop-syncing-relink-and-unselection), [Disconnect, reconnect and revoke](#disconnect-reconnect-and-revoke) and [Erasing a device or hub](#erasing-a-device-or-hub).
- **The hub keeps everything.** The hub coordinates the catalog, revisions and distribution, and keeps full content objects and history even when its own visible copy is unselected. Unselecting never removes a share from the catalog.
- **Backup is optional and separate.** A desktop or server replica can keep a full backup of the hub, independent of its working folders; see [Backup](#backup). Phones never back up.
- **Phones are replicas only.** Mobile (phone and Fold) never acts as a hub or backup: no hub creation or administration, pairing-code issuance, promotion, archive download, backup acknowledgement or export. It keeps pairing, disconnect and reconnect, whole-folder two-way sync, conflict preservation, pause, local browsing, sharing and import, and hub history and restore for selected folders.
- **History.** Restoring a version creates a new revision. Accepted revisions are versioned, not every keystroke or intermediate save between scans. Deleted files can be restored while retention keeps them.
- **Single-owner trust.** All machines belong to one owner. Selected folders limit what a client does locally, not the authority of an authenticated replica credential; a per-device folder ACL is not part of the model. Role gates still forbid hub administration from replica credentials.
- **License.** Arca is free for personal and non-commercial use under the PolyForm Strict License 1.0.0 (`LICENSE`, Required Notice Satoshi Ltd.): using it is allowed, modifying and redistributing it are not, and the README grants permission to modify and copy it only to prepare a contribution. PolyForm Strict is not an SPDX id, so the three `package.json` files say `SEE LICENSE IN` the `LICENSE` file, while the desktop crate, the iOS pod and the Docker image's `org.opencontainers.image.licenses` label use `LicenseRef-PolyForm-Strict-1.0.0`; the Umbrel description names the license. The Docker build context never includes `LICENSE`, because the local deploy scripts stage a fixed file list. Product and site copy say free and source public, name the license, state that business use is not covered and never claim Arca is open source (saying it is not is fine).
- **Vocabulary.** The product says **Device** and **Devices** for phones, tablets, computers and servers, **Hub** for the one that keeps the folders, and never Machine or Replica to a person: only the hub carries a role label. **Folder** or **shared folder**, never share or volume. **Start syncing** and **Stop syncing** (on the hub, **Stop syncing here**). **Version** in prose and buttons (Version history, Older versions), with `revision` kept for the counter, the protocol and the API. **Pair a device** on the hub and **Connect to hub** on a device; **Remove device** on the hub and **Disconnect** on a device; **Erase this hub** and **Erase this device**. `machine`, `replica`, `revision` and `volume` identifiers in code, API routes, CLI commands and this document's protocol sections are internal names, not product wording. All product copy is English through phases 1 and 2; user names, paths and file contents are preserved. Internationalization is phase 3.
- **Paused.** Automatic machine linking, including a same-Tailscale-owner policy, is not in the target. Discovery only identifies candidates; there is no automatic hub selection, code-free linking or Tailscale web login.
- **Music libraries.** Only the hub makes a folder a music library (a gallery can also come from a phone linking an album); a folder is one or the other, never both. Every device that selects it keeps the whole folder as usual. Desktop, web and phones browse it by artist, album and what they played recently; Android plays it with lock-screen and car controls, and Android Auto browses it. iPhone browses it and opens tracks in other apps until it gets a player (ROADMAP MOB-MUSIC-IOS); CarPlay and native Now Playing on desktop are later phases (ROADMAP MUSIC-CARPLAY, DESK-MUSIC-NATIVE). Playlists are `.m3u8` files Arca writes in the music folder's `Playlists/` directory, one track per line by path relative to the file, so they sync to every device like any file and still work outside Arca; files placed there by hand (`.m3u` or `.m3u8`) are read too, and only `.m3u8` files are edited.
- **Photo libraries.** Linked albums collect and replicate original photo files. They do not migrate an existing Immich library or offer a server photo-search experience; keep Immich until its archive and real-phone uploads are verified independently.

Example: the hub creates `iPhone Images`; a desktop selects it at a path it chooses; a phone selects it inside app storage and can link an album to upload into it. Photo-library access is a separate, permissioned feature, never implied by selecting a folder.

### Exclusions and limits

- No multi-user collaboration, public sharing links, automatic hub election or migration, virtual filesystem, binary delta protocol, or end-to-end encryption against the trusted hub.
- Symlinks, ACLs, permissions, extended attributes and resource forks are not synchronized. Renames travel as a delete plus a create (the hub rename operation records both revisions together). Open application databases are not transactionally synchronized.
- Unix sockets are local endpoints: scans skip them without reading, copying or deleting them, while regular files ending in `.sock` synchronize. If an indexed file becomes a socket, sync stops rather than publish a false deletion, and incoming content never replaces a socket. Other unsupported file types need attention.
- Content objects are reclaimed by garbage collection, not secure erasure. A share rename keeps its ID and every physical path. Folder relocation is explicit and keeps the original.
- Live Photos: the still and the motion file are uploaded and deleted as one registered group, but the gallery shows them as separate items and never pairs or animates them.
- Arca's `.arca-` bookkeeping paths and unsupported file types are safety constraints, not configurable exclusions.

## 2. Architecture and access

| Component     | Responsibility                                                                                  |
| ------------- | ----------------------------------------------------------------------------------------------- |
| Daemon        | Persistent identity, catalog, local scanning, transfers, revisions, materialization and API     |
| CLI           | Auxiliary installation, startup, diagnostics, web sign-in codes, offline recovery and scripting |
| Tauri desktop | Local daemon administration, onboarding, tray and opening local folders                         |
| Web           | Administration of the daemon serving the page, with the same frontend as Tauri                  |
| Expo mobile   | Replica with persistent app-owned files and OS-aware synchronization                            |

**Web is the primary server administration.** Daily folder, machine, backup, history and settings workflows are available there; Tauri shares them while managing its local daemon. The CLI is an auxiliary tool: no interactive terminal menus, no duty to mirror every screen. Installation and offline recovery may need a shell.

The daemon is JavaScript on Node 24 with SQLite in WAL mode, persistent IDs, a state lock, SHA-256 content objects and a revision index. There is no TypeScript. Only the current schema and protocol are supported: fresh databases create the full schema, and there are no migrations for pre-production state.

### Service port

One port per machine, **17831/TCP** by default, for desktop, Docker and Umbrel. Existing explicit configuration is never silently overridden at startup.

| Path                          | Purpose                                                       |
| ----------------------------- | ------------------------------------------------------------- |
| `/`                           | Web UI (server installations only)                            |
| `/auth/login`, `/auth/logout` | Browser session                                               |
| `/v1/*`                       | Authenticated management and synchronization API              |
| `/.well-known/arca`           | Minimal discovery metadata, without file paths or credentials |

Discovery additionally returns `access.codeDigits`, `codeExpiresInSeconds`, `networkMode`, `daemonTransport`, `allowLanHttp` and whether an authorized web approver exists; none of these exposes a secret or a path.

### Installation and role

Installation and role are independent. The staged desktop runtime is stamped `arcaInstallation: "desktop"` by `stage-runtime.js`, and startup persists `installation: "desktop"`; source and server runtimes are `server`. `daemon --setup` requires a server installation.

A desktop installation serves no browser UI, assets, `/auth/*` or `/v1/web-sessions/revoke` (all 404), rejects `web-code`, and refuses browser-origin requests to its API. Its native bearer API, discovery, pairing (on desktop hubs) and synchronization stay available. Server installations keep the web UI and browser sessions whatever their role. Tauri's WebView and the Vite dev server are not daemon-hosted administration. Tauri keeps the local admin credential in its native bridge; the desktop has no browser session to sign out of.

### Network trust

- **Standalone** listens on loopback by default. Non-loopback binding needs an explicit encrypted-network or TLS-proxy deployment flag. Never expose the plain HTTP port to the Internet.
- **Tailscale mode** adds an address-specific listener while Tailscale is connected and restricts remote access using current tailnet status; it does not replace application authorization. Docker reads a sanitized, read-only Tailscale status file, never the control socket.
- **Verified Tailscale routes.** For non-loopback HTTP without an explicit trusted-network option, the client reads current Tailscale status, resolves the hub hostname and requires every resolved address to be a known tailnet peer or self inside a Tailscale range. It pins the request and the saved hub URL to that verified IP, so credentials never follow a second DNS answer. Unknown or mixed addresses and a disconnected tailnet are rejected before any pairing code is sent. HTTPS keeps normal certificate validation. Pairing, catalog and sync requests reject redirects. This verifies the route at connection time, not every later network change.
- **Local network HTTP** is a hub-only opt-in (Settings → Network → **Allow HTTP on local network**, off by default, `network.allowLanHttp`). A private IPv4 socket peer (10/8, 172.16/12, 192.168/16) needs it for HTTP pairing and every device-authenticated request, also in Tailscale mode. Disabling answers later requests with 412 and keeps credentials and files. The policy uses the real socket peer, never forwarded headers, so a TLS proxy arriving from a private address also needs it. It is not a firewall, binds no interface and publishes no port. HTTP is unencrypted: others on that network can read files, codes and credentials.
- **Clients on a LAN.** Mobile and desktop accept a literal private IPv4 address only after a credential-free discovery check confirms the hub allows it. Android binds LAN requests to a Wi-Fi or Ethernet network handle (preferring the active network, skipping restricted handles and reselecting once if binding fails before the body is written); iOS checks the route against an active local `en` interface and refuses cellular. No DNS discovery or automatic LAN host selection exists.
- **HTTPS reverse proxy.** Set `ARCA_WEB_ORIGIN=https://arca.example` to the exact external origin; the proxy preserves Host and restricts its backend. Arca then checks Origin and Host and sets Secure cookies. This does not provision certificates, and Tailscale HTTP is never labelled TLS.
- **Discovery** caches Tailscale status and scans for 15 seconds, probes at most 128 peers four at a time and sends no credential. Status snapshots older than 90 seconds are unavailable; an app heartbeat expires after 30 seconds.

Errors carry a `code` when one applies. A stale Tailscale status answers 503; an unknown peer on a connected tailnet gets 403.

### Authentication and pairing

| Access             | Behavior                                                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Web administration | Six numeric digits (leading zeroes kept), single use, ten minutes from generation. The session ends at sign-out, after 24 hours or on restart. |
| Local desktop/CLI  | The local administrator credential of the OS user; Tauri keeps it in the native bridge. No manual login.                                       |
| Machine pairing    | The hub administrator generates a separate six-digit, ten-minute code; redeeming it creates a long, revocable machine credential.              |

- Codes accept spaces and hyphens (`381-924` is a valid-format example). One code per purpose is active; a new one invalidates the previous. Web and pairing codes are not interchangeable. Admin, session and machine tokens are long secrets.
- Generation is cryptographically random; expiry and single use are enforced on the server, and consumption is atomic so only one concurrent redemption succeeds. Five wrong attempts invalidate the active code, and failure budgets survive restarts. Each endpoint also allows five requests per source address and fifty in aggregate per minute; a new code does not reset these windows. Throttling answers 429 with a one-minute retry; invalid, expired and used codes share one 401; an exhausted budget answers 429 asking for a new code. No remaining-attempt count or expiry timestamp is exposed.
- A reachable attacker can exhaust a short-code budget on purpose, so access belongs on trusted routes. The design follows OWASP's token guidance: randomness, hashed storage, single use, expiry and rate limiting.
- Browser sessions are HttpOnly, `SameSite=Strict` cookies; same-origin checks guard every mutation. A browser page never mints its own code, sends email or SMS, or reads SSH credentials. Signing out browsers never unlinks a replica or revokes its sync credential.
- **Web approval.** An administrator can grant individual linked devices web-approval authority in Devices. The login page can then create a ten-minute request; foreground desktop, web and mobile clients with that authority poll every three seconds and show Allow/Deny with a comparison reference, the socket-observed IP and the requester-reported browser. The first valid decision wins and other prompts close on their next poll. Creation, poll and cancel are unauthenticated same-origin POSTs; consuming or cancelling needs a separate random requester secret that pending lists omit. Creation is rate limited and capped, and requests die at expiry or restart. The approver's permission is rechecked at redemption, and the granted session uses the normal cookie. This permission is administrator-equivalent for browser access and never follows from sync access. Replica daemons proxy approvals with their machine credential; the hub enforces authority. A replica never replays a saved request: while the hub is unavailable (or slower than 3 seconds) it reports none with `offline: true`, drops expired requests, and deciding answers 503 at once when the hub is known unavailable (10-second deadline otherwise); an offline answer neither opens nor closes a prompt in the UI. There is no background push.

From a terminal with SSH access to a Docker server, a web code comes from `docker exec <container> node packages/cli/arca.js web-code`.

### Discovery and authority

- Tailscale discovery identifies Arca candidates and their reported roles. It never installs Arca, chooses a hub, authorizes a machine, selects folders or starts sync. Discovery never links machines.
- Unlinked machines appear only after a valid Arca answer, including an incompatible version, which is not pairable. Unrecognized tailnet peers are excluded. Previously linked devices stay known while offline; silence is not uninstallation.
- Tailscale is an attribute in one Devices inventory, never a separate authorization model. Standalone and Tailscale both need explicit pairing.
- **Only the hub administrator issues pairing codes and removes machines.** A linked replica never gains the right to invite others. Discovery can prefill a detected hub address for an unlinked replica; pairing from another replica, remote hub-admin switching and one-click two-way pairing do not exist.
- Issuing a credential is not proof of connection, and authenticated contact is not proof that selected folders are current.
- Connecting to a different hub with existing local state requires explicit replacement-hub reconciliation; nothing silently switches hubs.

### Machines and reports

`GET /v1/machines` gives authenticated linked devices and hub administrators the hub's read-only roster: current registrations, last authenticated contact, backup acknowledgements and optional machine reports. A replica's local administrator reads it through its daemon. It grants no remote administration. Invited and authenticated states stay distinct; removed credentials are absent and no revoked list is kept.

- Reports (`POST /v1/machine-report`, linked credentials only, sanitized counters) carry selected folder IDs and totals, indexed files and bytes, `albumFolderIds` for album-linked folders, coarse platform, kernel release, uptime, last completed sync and server receipt time. Clients send them after successful cycles at most every 15 seconds, and immediately after selection, unlink or a machine rename, even while paused. They become stale after two minutes; missing reports stay unknown. They are not a heartbeat, an OS version lookup, disk usage, revision lag or proof that files match. Credentials and local paths are never included, nor album names or library content.
- `GET /v1/catalog` also returns the caller's own device id and every registered device's id and name, revoked ones included so old revisions keep a name. A replica keeps them (`status.deviceId`, `status.hubDevices`) so History, Recent and file detail name each author, its own changes included, without a pairing token or any other secret.
- A backup acknowledgement is the last reported enabled/revision/time state, not an integrity audit. No acknowledgement means unknown, not disabled.
- Tailscale connectivity is not TLS. Discovery exposes the configured network mode and daemon transport, not browser-side TLS behind a proxy. A Tailscale label needs discovery evidence; a 100.x address alone proves nothing.

### Disconnect, reconnect and revoke

- **Disconnect** (`POST /v1/disconnect {confirmed:true}`, replicas only) pauses cooperatively, interrupts scanners, waits for the running cycle, removes its own registration through `POST /v1/leave` (no arbitrary machine ID), then clears the hub token and the optional backup token and disables backup. Local folders, files, indexes and destinations stay, and an existing user pause is preserved. The request has a five-second timeout; failure keeps credentials for a retry and restores the previous pause. Status then exposes `disconnectedHub` (hub ID and URL) and the last `hubName`.
- **Remove device** (a device's actions menu on the hub, `POST /v1/revoke {id}`) deletes the machine's row (name, credential hash, last address and contact), report, backup acknowledgement, snapshot leases and rows, and partial uploads. Queued work rechecks authorization when it starts and POSTs recheck after reading the body, so a request authenticated before removal cannot recreate reports or uploads. Delivered bytes cannot be recalled. Files, revision history and opaque author IDs in revisions stay; conflict filenames, backups and config checkpoints are not rewritten. Removing the backup acknowledgement also drops that machine's retention hold. Both revoke and leave interrupt the active background cycle instead of waiting behind a hub scan.
- A rejected credential (401) clears the replica's connection at its next authenticated contact; offline or paused replicas notice after they return.
- **Reconnect** redeems a fresh pairing code with `POST /v1/connect`, keeps selections and marks them for reconciliation; offline edits reconcile. It never enables backup. Switching to a different hub ID with saved folders requires explicit replacement-hub recovery, which clears incremental cursors with the indexes and keeps a recovery checkpoint.

### Erasing a device or hub

Both live in Settings → Danger zone, need explicit confirmation and share one installation-reset journal. They work offline.

- **Erase this device** (`POST /v1/destroy-replica {confirmed:true}`, replicas, including disconnected ones) interrupts sync, drains cancelled work and tries to remove the hub registration with a one-second deadline, then permanently deletes the registered local folders (unsynced changes included), the configured full backup, transfer objects, derivative caches, indexes, queues and recovery checkpoints. Unrelated files in the default root, exported files and copies no longer registered are outside it. Hub content and other machines are untouched; an unreachable hub may keep a stale machine entry to remove there. Mobile does the same for its app-owned folders, partial transfers and incoming staging, clears credentials and catalog, resets its database and returns to first run; nothing in Photos or on the hub is touched.
- **Erase this hub** (`POST /v1/destroy-hub {confirmed:true}`, local admin) stops sync and gallery work and deletes the hub's registered folders, configured backup data, objects, caches, history and device state. It never emits tombstones or deletes replica copies: replicas keep their files, and their old credentials become unauthorized.
- The journal permits retry after a partial cleanup and resumes on startup. Changed directory identities and symlink substitutions are refused rather than deleting a replacement directory. Pending destruction blocks sync and mutations. Success rotates the machine identity and admin credential, clears browser sessions and returns to `needsSetup`, keeping the listener and default root so the daemon stays reachable. Authenticated `POST /v1/setup` then accepts a new name, role and root only in that state; server web access needs a fresh web code.

### Onboarding

- **Desktop:** welcome → this device (name and role on one page, with a line on who each role is for) → pairing → folder root → Finish; hubs skip pairing. The rail reads This device, Connect and Folders, and Connect reads Not needed for a hub. The daemon starts in a durable onboarding state and blocks sync until Finish. Pairing saves the accepted credential before fetching the catalog, so a catalog outage or reload never needs the consumed code again. The final root must be empty or new; the check verifies canonical ancestry against state and reports real free space without creating the directory. New roots and suggested destinations default to `~/arca`.
- **Mobile:** welcome → pairing (hub address, six-digit code, machine name) → first-folder selection, with Skip for now. Destinations are app-owned, so there is no destination step. Credentials are saved first, the onboarding marker survives retries, automatic sync waits for selection or Skip, and selection preflights the total space. A device with a retained catalog enters the normal offline interface instead.
- **Web** uses the desktop wizard when setup is required; browser authentication stays separate.

#### Server onboarding

An unconfigured server opens the shared welcome wizard even without a web session: welcome → this device (name and hub or replica) → confirm administrator access (under This device in the rail) → pairing (replicas only) → persistent folder root → Finish. Name and role stay tentative browser values until the wizard asks for the existing single-use web code, before any configuration is saved. Umbrel links to its app-password code page in another tab; ordinary Docker shows the command `docker exec <container> node packages/cli/arca.js web-code` with a Copy button and says the code is the `code` value of its JSON reply. Authentication and CSRF guard every setup mutation, and accepted progress resumes from the server after sign-in. Replicas select whole folders after setup; sync stays idle during it. Configured-server login offers machine approval only when discovery reports at least one authorized approver.

`packages/daemon/setup.js` owns `initializeServer` and root inspection. Docker runs `daemon --setup` with `ARCA_FILES=/data/files`: existing server configurations start unchanged (identity, role, pause, data), empty state becomes a provisional replica with `needsSetup` and no hub or backup, and incomplete state without a config is refused. The root must be empty, writable and resolve inside `ARCA_FILES`, symlink escapes included; custom containers set `ARCA_FILES` to their durable files mount. The wizard explains that the destination is on the server. Explicit `init --role hub|replica` still works.

## 3. Synchronization

The implementation (`packages/daemon/server.js`, `storage.js`, `engine.js`, `snapshots.js`, `network.js`, `tailscale.js`, `web.js`, and `apps/mobile/src/replica.js`) is authoritative for exact request validation; this section states the contracts it must keep.

### Protocol

- **Ordering.** The hub orders revisions. A proposal (`POST /v1/propose {volume,path,base,hash,size}`, `hash:null` for a deletion) compares the caller's base revision with the current head; concurrent content becomes a conflict copy, never a silent overwrite. Replica cycles capture local changes before applying remote ones. Content objects are immutable and SHA-256 addressed.
- **Uploads.** Clients ask the upload status, then `PUT /v1/uploads/HASH?offset=N&size=N`. The status advertises `maxChunkBytes` (8 MiB); desktop and server replicas honor it, falling back to 1 MiB when absent, while phones always use 1 MiB blocks; JSON bodies stay capped at 1 MiB and objects at 100 GiB. The hub accepts a finished upload only after hashing the bytes stored in its part file, asynchronously, so damage on disk between blocks is rejected. Status and completion verify an existing object's hash and size; a verified new upload atomically replaces damaged content, and a desktop replica can download a verified replacement for a damaged local object.
- **Downloads** use range requests (`blobRanges`) with resumable offsets and full-hash verification. A resumed transfer rejects a hub that ignores Range.
- **Change feed.** `GET /v1/changes?volume=ID&after=REV[&through=REV]` returns up to 500 current file and tombstone rows changed after the cursor, bounded by a fixed upper revision, with a `next` continuation; the catalog advertises it as `changes:true`. Changes that arrive during pagination come on the next check. A cursor advances only after the folder's received work is applied; invalid cursors and policy changes request reconciliation. The published window stops before pending materialization, including the earlier tombstone of an atomic case rename, and clients cannot acknowledge revisions missing from the accepted index.
- **Snapshots.** Full reconciliation, first downloads and backup workers read immutable paginated snapshots (`GET /v1/snapshot`, always paginated). Rows are captured through the scanner worker on a read-only SQLite connection and persisted in bound multi-row inserts of 2,000, yielding between short transactions; overlapping captures of one folder generation share the read while each requester gets its own authenticated lease. The lease belongs to the requesting machine, expires ten minutes after its last page read, stores its entry total so later pages and restarts never recount, and pins its objects: collection waits while captures are built. `/v1/snapshot` checks the lease cap and registers disconnect before scanning and skips abandoned requests. A machine's new first page replaces its own lease for that folder; admin leases are independent. Waits answer 429 or 409 with codes such as `SNAPSHOT_BUSY` and `SNAPSHOT_EXPIRED`. Cancellation, expiry and lease removal clean up interrupted construction. The tombstone replacement lookup uses the `(volume, path_key)` index. Snapshot totals count entries, not visible files.
- **Capabilities.** The catalog advertises `directories:true`, `pathTransitions:true`, `changes:true`, `blobRanges`, `gallery` and `galleryDeletion`. Sync clients send `X-Arca-Directories: 1` and `X-Arca-Path-Transitions: 1` on change, snapshot, archive and proposal requests; the hub answers 412 to linked clients without them, even for file-only folders, so null-hash directories are never read as deleted files. Clients refuse hubs without the capabilities they depend on (see [Current state](#current-state)). Case-renamed tombstones carry a `replacementPath` to their live successor, snapshots included.
- **Retries and receipts.** A proposal scans before consulting the response cache and reuses a response only at the same folder revision; conflict names distinguish intervening revisions. The cache holds 10,000 responses and share deletion clears its entries. Separately, compact acceptance receipts are written before each mutation and survive cache eviction, restart and history retention; they disappear with their share or an installation reset. A stale proposal may continue a lost reply only when a receipt proves the current head was accepted from the same replica on the same base. A request repeated after its first acceptance never takes that shortcut: stale deletions are rejected and stale writes become conflict copies. An interrupted receipt or an older head without one conservatively conflicts; missing foreign history is never evidence of ownership. A replica records each accepted proposal in its index immediately, so an interrupted cycle re-proposes only unaccepted changes.
- **Events.** `GET /v1/events` is authenticated ten-second long polling over an opaque catalog, revision, pending-write, hub-availability, phase, error and pause signature (so a window learns that the hub left or returned within about a second), served by one shared 500 ms sampler with bounded waiters that disconnect or shutdown release. Credentials and sessions are rechecked before delivery; it answers 412 when LAN access is disabled. Events are hints: snapshot and change cursors stay authoritative, and periodic checks remain the fallback. Replica daemons wake on hub changes; desktop and web views react to local events; a successful poll ends offline backoff.
- **Connections.** The daemon's HTTP keep-alive timeout is 30 seconds, longer than clients keep idle sockets, so a reused connection is never closed mid-request.

### Integrity guarantees

| Area                               | Contract                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Proposal retries (SYNC-01)         | Scan before the cache; reuse a response only at the same folder revision; receipts decide lost replies (above). Unlink and reselect with recreated identical bytes never undo a hub deletion: relinking trashes the stale copy before proposing anything.                                                                                               |
| Offline recovery (SYNC-02)         | Recovery never seeds `.arcaignore`. The archive supplies policy and content; fixed-excluded history rows are counted but never written. Pending recovery orders removals before creation and parents before files.                                                                                                                                                                   |
| Incremental publication (SYNC-04)  | The published change window stops before pending materialization; clients cannot acknowledge revisions missing from the index.                                                                                                                                                                                                                          |

Evidence lives in `tests/protocol-integrity.test.js`, `tests/mobile-replica.test.js` and the sync, recovery and authorization suites. Also: any HTTP answer from the old hub blocks promotion of a replica; removing a remote ignore policy applies before scanning and triggers reconciliation; mobile recomputes queued operations after a complete inventory so a recreated file cancels an obsolete deletion even with the old bytes; desktop flushes a conflict copy and its parent before removing the original; relocation validates without creating the destination and verifies a private staging copy.

### Scheduling on desktop and server

Working sync uses a persistent SQLite dirty-path queue and a persistent remote cursor per folder.

- **Local events.** Already-ignored events are dropped by the current policy. Others are deduplicated for 1,000 ms and flushed to SQLite in a batch; only affected paths and subtrees are scanned, and deletion checks stay within the same scope. More than 2,048 pending paths, unknown event filenames or a root `.arcaignore` change request complete reconciliation. Events received during work keep their queue sequence; a restart registers watchers and requests a full scan, covering the pre-flush crash window.
- **Watchers.** `packages/daemon/folder-watch.js` keeps macOS and Windows on one native recursive watcher per folder. Linux (Docker, Umbrel, Linux desktops) watches each non-excluded directory individually (`.arcaignore` plus the fixed list), adds and drops directories as they change and rebuilds on a root `.arcaignore` change, because Node's recursive watcher spends inotify watches on excluded trees and can exhaust the user-wide limit. Exhausting it anyway falls back to periodic full reconciliation, and an error raised later by an existing directory watcher is reported like a failed registration: the folder is marked for a full scan within a second, the watcher is dropped and a new one is created only after the 60-second retry pause. Mobile engines have no watchers.
- **Replica cadence.** Remote checks run every 15 seconds, stretching to 60 seconds after five idle minutes. Operation failures back off from 30 seconds to five minutes; connection failures cap at 60 seconds with jitter, and a successful event poll ends that backoff. An event poll that fails at the transport level asks for a cycle at once (the cycle, not the event, decides connectivity; an HTTP error answer, such as a busy hub's 503, asks for nothing). While offline, the replica probes the hub with an event request that is not held (no cursor, 5-second deadline) and pauses 5 seconds after each probe, so a returning hub is noticed within about 10–15 seconds. Watcher events do not bypass the delay. Sync now retries at once and requests full reconciliation. Cycles never overlap; work that arrives mid-cycle gets a follow-up.
- **Hub cadence.** The hub checks for due work every 60 seconds without scanning clean folders. Startup, watcher loss and a six-hour safety interval trigger full reconciliation. The service never wakes a sleeping machine; OS suspension pauses timers.
- **Scan cache.** A file whose signature (device, inode, size, nanosecond modification and change times) matches its cached capture is not copied or hashed again, however old the capture; content is re-read only when the signature changes. Startup, six-hour and Sync now reconciliations therefore stat unchanged files. The scanner hashes in a worker thread with a persistent metadata and hash cache and periodic verification every one to two weeks.
- **Incoming safety.** Paths outside the local scan are checked before materialization. A missed local edit is queued for upload or conflict handling without advancing the cursor or overwriting it.
- **Interruption.** Pause, unlink and delete interrupt worker scans between files and hub catalog work between commits. A partial scan is never a complete inventory. One file copy or hash, an in-flight request or a synchronous database operation can still delay interruption.
- **Browsing and totals.** `browsePage` reads a prefix through the `(volume, path)` key range. Reads trust the index because excluded paths are not indexed: browsing and totals are plain SQL, totals over the `files_visible_totals` partial index that excludes tombstones and directories. Folder-total cache generations change only with that folder's index; policy changes invalidate independently, and heartbeats or gallery writes never reload file rows. A desktop or server replica also keeps `local_files`, a derived table of what its own disk holds that the index does not (new and edited files with the index's revision as their base, or 0, and deletions as deleted rows), and `files_view` overlays it on `files`: browsing, folder totals, the gallery, the music library and its playback, file details and the actions on a file read the view, while synchronization, pull and materialization only ever read `files`. The table is rebuilt by scanning the touched paths (from folder events, after Rename, Delete and playlist edits, and when a cycle fails or the replica is paused; a full scan once per start and after a lost watcher) whether or not the hub answers, bumps the folder's file generation like `files`, loses a path when the hub's accepted row for it arrives, and is emptied for the paths a successful cycle acknowledges.
- **Transfers.** Desktop and server replicas stage at most three nonempty file blobs at once; policy changes, directories and empty files stay sequential, and proposals are still sent in original order after staging. Identical hashes in a batch share one upload. A failure waits for in-flight work before leaving the folder; pause and unlink abort requests and prevent publication. Upload blocks shrink after a timeout (down to 256 KiB) and grow after fast blocks; downloads use a 60-second no-progress window.

The UI status loop and Tailscale discovery are separate from file synchronization. Timing defaults change only after P1-SCHEDULER measurements.

### Storage

- **The hub** keeps a permanent content store; its visible folders are independent materialized copies of it.
- **A replica keeps each file once**, in its working copy. Its object store holds only transfers in flight: a changed file from capture until the hub accepts it, a download until it is written to the folder, plus the small `.arcaignore` policy object. A scan trusts an unchanged signature whose hash the hub already accepted without keeping that object. Downloads are fetched only for rows that differ from disk, and identical files in a pull share one download. A phone moves the verified object into place, so applying a file never holds two copies, unless a queued upload still needs those bytes; a later identical row of the same folder's pull copies from the file already placed after its hash is checked (the same bytes in another folder download again). A captured change still waiting for the hub keeps its object and signature across an interrupted cycle. Each replica cycle and each unlink collect every other object.
- **Backups** keep their own permanent store (see [Backup](#backup)). Hub history cleanup forgets only the scan signatures of removed objects. Promotion clears the scan cache so the new hub captures every file into its store.
- Hardlinks and reflinks are not used: a hardlink to an externally editable working file would break object immutability, and two copies on one disk are not disaster recovery.
- Seven-day abandoned-partial cleanup and a 16 MiB free-space margin apply; there is no quota or reservation against concurrent external writers. Local scan maps grow with folder size and some materialization and relocation I/O is synchronous.

### Directories

Scans keep explicit directory entries, including nested empty directories and directories holding only excluded metadata. Rows store `directory=1`, `hash=null`, `size=0`; live directories and tombstones stay distinct. Snapshots, changes, mobile's durable queue, backup, recovery and promotion carry the type, and no placeholder files are created. File counts, bytes and activity exclude directories; explorers show directories with zero files.

Directory deletion applies children before parents and is non-recursive: remaining local or excluded content is preserved and reported as an error. A stale deletion never removes a recreated directory. Concurrent file/directory type changes need explicit reconciliation. Exclusion rules apply to directories. Mobile removes directories with non-recursive native calls (`Files.delete` on Android, `rmdir` on iOS). New directories are checked against an indexed lowercase path key, which also guards Unicode case collisions, literal `%` prefixes and file/ancestor/descendant boundaries.

### Names and paths

Catalog paths use NFC identity. Composed and decomposed filenames are accepted without renaming local entries, and filesystem lookup resolves canonical-equivalent spellings. Distinct equivalent entries, traversal, reserved names and case collisions stay blocked and name the offending path. Filenames are limited to 255 bytes and must be single portable components.

### Conflicts

Concurrent content is kept as a conflict copy next to the original, both with their histories. `POST /v1/conflict-choice` restores the chosen version as a new revision only when both reviewed revision IDs still match, and atomically records a `conflict_resolutions` row. Catalog counts and history filters then show the copy as resolved instead of pending; editing the conflict copy again reopens it. Conflict-copy revisions are excluded from the default activity list. Replicas resolve only folders selected locally and included in their hub report; stale choices change nothing. Keep both and Cancel record nothing. In the web interface the dialog offers a download link for each version: the hub serves its own objects (`/v1/blobs/<hash>`), a server replica serves the copy it holds (`/v1/gallery/download?volume&path&hash`) and shows the link only when its local file is that version, and the native app opens both files instead.

### File operations

- **Delete** (`POST /v1/delete-file`, local admin) rejects backup credentials, unselected replica folders, directories and stale revisions. The hub scans current content and records a restorable tombstone; a replica first rescans the path, so a change made on disk counts, then deletes its local file and propagates through normal sync, moving a file whose content no live row holds (never synced) to the system Trash instead of unlinking it, and refusing when the Trash fails. Mobile deletes the file whether or not the hub ever received its latest content, after a confirmation that says the change cannot be undone when it never reached the hub (`hasUnsyncedContent`); the next sync proposes the deletion only when a synced row exists.
- **Rename** (`POST /v1/rename-file {volume,path,name,rev}`, local admin) works on the hub's selected and catalog-only folders and on a replica's selected folders. It changes only the final path component; portable-name validation, revision and content checks and case-insensitive destination checks reject stale files, directories, occupied names, excluded destinations and the root `.arcaignore`. The hub records both revisions atomically and journals the physical change, withholding the pair from publication until complete; recovery writes the destination before removing the source, and catalog-only renames leave unselected files alone. Case-only renames use the path-transition contract. Desktop replicas rescan the path first and rename the local file it holds, one added or edited on disk included (its `rev` is the index revision it builds on, or 0 for a file the hub never saw), and sync; phones rename verified app-owned files, also offline. History stays path-based: older revisions remain under the previous name.
- **Restore** (`POST /v1/restore {volume,path,rev}`) creates a new revision; backups never restore upstream.
- Delete, restore, conflict choice, move, ignore-policy edits, gallery link, machine removal, retention and backup actions interrupt the active sync cycle before entering the serialized work queue. Scans stop cooperatively and outgoing sync requests abort; partial transfers and unacknowledged cursors stay retryable. Successful actions schedule sync promptly; a user pause stays. Daemon sync requests inherit cancellation from their cycle's async context, while independent interface requests to the hub do not.

### Stop syncing, relink and unselection

- **Stop syncing on a device** removes the local mapping, local index and matching `.arca-volume` marker, and stops sync for that folder on this device; the hub keeps the folder, files and history. The dialog's one inline option, **Delete the files on this Mac/device**, is on by default so a stale copy cannot come back as local content on a later relink; with it on the action reads Stop syncing and delete, with it off Stop syncing, which keeps every file, `.arcaignore` and conflict copy. Deletion first lists the folder's accepted files and directories that the current `.arcaignore` does not exclude, commits the unlink, then deletes from that closed list, so a failure can never be proposed as a deletion. Each file goes only after a fresh hash matches the accepted version; excluded, edited or new files, anything reached through a symlink and anything unverified stay. Only hub-known directories are removed, when empty or holding only OS metadata (`.DS_Store`, `Thumbs.db`, `desktop.ini`); never-synced empty folders stay. The result reports deleted files and bytes and how many remain, and leftover files are no longer reported as managed copies.
- **Relink** is a fresh selection with the hub as the source of truth (`Engine.setAsideStale`). Until the folder's first sync completes, local files the index does not know are compared with the hub's current rows, read from `/v1/changes?after=0` so deletions count. Identical files are adopted and files the hub never had upload. Files the hub deleted or holds in another version go to the system Trash (`packages/daemon/trash.js`) before anything is proposed, and the hub version downloads. Each volume uses its own trash, as the OS does, so nothing is copied across disks: on macOS `~/.Trash` or `<volume>/.Trashes/<uid>` (no Finder metadata, so Put Back is unavailable); on Windows the Recycle Bin on fixed drives only, refusing files when the bin is off (`NukeOnDelete`) or smaller than the file (`MaxCapacity`), with PowerShell bounded to 120 seconds; on Linux the freedesktop home trash or `$topdir/.Trash-$uid`. Docker sets `XDG_DATA_HOME=/data/state` so a container's trash persists. If a file cannot be trashed, the folder stops with an error naming the files to move by hand, proposes nothing, and reuses the fetched hub heads for ten minutes instead of re-reading the hub each cycle.
- **Hub local-copy unselection** (Stop syncing here) stops updating the hub's physical working directory; the share, content and history stay available to replicas and files stay on disk. It never deletes files.
- **Delete share** (`POST /v1/delete-share {id,confirmedName}`, hub admin) needs the exact name and removes the catalog and history registration; physical files and existing backups remain. Replicas detach after refreshing the catalog and keep their files. Removing a directory by hand never deletes a registration.
- **Share rename** (`POST /v1/rename-share {id,name}`) validates portable, case-unique names and changes metadata only; replicas and backups receive it on their next catalog sync.
- **Pause** acts on the whole machine and keeps every link; it is never per folder and never deletes data or stops the daemon. `POST /v1/pause` takes an optional bounded `seconds`. Interruption is cooperative between operations and chunks. A user pause is never resumed automatically, including by deployments.
- **Relocation** (Change location…, `move-folder`) copies into a new destination, verifies the contents and keeps the original; the destination must be new. Stop external writers first.

### History retention and cleanup

Each folder has a retention policy: Off, 1 day, 1 week, 1 month (30 days) or Forever, defaulting to 30 days when none is stored; explicit choices are kept, and gallery status never decides retention. Only hub administrators preview and apply it (`/v1/folder-retention`); the catalog reports `historyRetention` to replicas.

- A rolling window starts when a version is superseded by an edit or deletion, not when its content was created. Off removes superseded revisions; current files, current tombstones (so an offline replica still learns the deletion), pending revisions and history not yet acknowledged by an enabled backup are always protected. Forever cannot recover history already removed.
- Policies run hourly during unpaused hub cycles and when applied. Interactive retention reads only the requested folder, reuses its confirmed plan and leaves object collection to scheduled maintenance, which collects once after evaluating every folder, even when all are Forever.
- Garbage collection removes only unreferenced objects older than 24 hours; shared hashes, current files, retained history, pending writes, snapshot leases and backup history protect bytes. Retention never promises immediate disk reclamation and never erases other machines' backups.
- Manual global cleanup previews age and version limits and applies them only with the preview's digest (`retention --days --versions --confirmation`).
- Retention planning reads revision identity and timestamps only and aggregates per-folder counts in one pass; normal snapshots and changes read current heads, never retained history.

### Backup

A desktop or server replica can mirror the hub's content store into a dedicated directory while normal two-way sync continues.

- It keeps every hub folder's current files and the history each folder's retention keeps (Off keeps only current files, Forever everything). When the hub prunes, the backup prunes the same revisions and objects on its next cycle, and the hub never prunes a revision the backup has not copied. A folder deleted on the hub stays in existing backups, and pruning never empties a folder.
- The backup keeps only `state/` (history, identity and objects). A browsable `files/` copy left by older layouts is never scanned or published. The backup engine never runs the working-folder pass, so it can never scan or propose, and it never publishes edits.
- Enabling (`POST /v1/backup {enabled,path?}`, CLI `backup enable EMPTY_FOLDER` / `backup disable`) needs a missing or empty directory outside synchronized folders and daemon state. Inside Docker the location must be on a mounted volume; a path in the container's own filesystem is refused. A location whose `state/` vanished reports missing data, and Disable then Enable restarts there only while empty. A configured location that no longer exists is never recreated (it may be an unplugged disk), and the backup records its disk device, refusing an empty mount point on another device as "not mounted" so the system disk never fills silently.
- Archive access (`GET /v1/archive`, including historical revisions) uses the replica's existing credential. Backup errors are reported separately from working-folder sync; an unreachable hub leaves it waiting rather than failed. Pausing the machine pauses both. Enabling while the hub is unavailable stays enabled with a pending acknowledgement.
- Backup content size is cached as `backup.contentBytes` after successful cycles: unique non-null hashes in the retained backup history, counted once. It is not allocated disk space. Status reads never walk the disk.
- Public daemons and invitations are hub or replica only; there is no standalone backup machine. Recovery rebuilds a hub from `state/` (see [CLI and recovery](#cli-and-recovery)).

### Promotion and replacement hub

A replica with every last-known catalog folder synchronized can become the hub after explicit confirmation that the old hub is stopped (`GET /v1/promotion-plan`, `POST /v1/promote {confirmed:true}`). Pending transfers, unsynced or failed folders, missing paths and an enabled backup block it, and any HTTP answer from the old hub blocks it too; a reachability probe is a guard, not proof, since a partition can hide the old hub. Current files become a new history under the replica's identity; unseen remote revisions and old history are not recovered (use backup recovery for that). A promoted desktop stays a desktop installation. Other replicas reconnect with a fresh credential and `reconcile:true`, keeping files and submitting differences as conflicts; their folder IDs must exist on the new hub and backup must be off. A SQLite checkpoint precedes either transition and a durable journal reconciles configuration after a restart. There is no automatic election, demotion or redirect.

### Connectivity and offline behavior

- Connectivity is classified by error code first (`HUB_UNREACHABLE`, `HUB_TIMEOUT`, `CONNECTION_LOST`, a hub-unavailable flag, gateway 502/503/504), then by transport text: route rewrites, interrupted connections, Android reset, broken pipe and `UnknownHostException`, Android `ConnectException` and socket timeouts, and iOS `URLError` texts count as outages. `FileNotFoundException`, "reconnect", picker and provider failures (`SOURCE_UNAVAILABLE`) and gallery export timeouts never do. Folders keep their last real issue instead of saving a connection error.
- Optional notifications never decide connectivity. Any successful ordinary hub response clears offline state, and an older failed request cannot override a newer success. Snapshots hide active folder and progress states while paused or offline, and an interrupted cycle clears remaining active markers. Pause overrides the displayed connectivity without resetting it; resuming does not declare the hub online until a request succeeds.
- A transport failure ends the current replica cycle instead of waiting once per remaining folder. Local file errors stay independent. On the phone this includes the music step after the folders: a hub that cannot be reached there ends the cycle, marks it offline and leaves the last-sync time alone. Calls the person is waiting on use short deadlines (the device-name report 5 s, Photo Info and the gallery index 8 s, the catalog probe 10 s) and are not made at all once the hub is known unreachable: Add photos… journals the picks and ends at once as hub-unreachable, and Change album… repairs a damaged record from the saved catalog (the hub link waits for the next cycle). The saved gallery index never queues behind a hub read.
- The cycle's small metadata reads (catalog, change pages, the policy history) have a 10-second deadline, so a hub that accepts connections but never answers, such as a Tailscale peer that is down, marks a desktop or server replica offline within about 10 seconds of a cycle, and between syncs within about 25 seconds through the event poll. An active transfer, proposal or snapshot page keeps its 60-second budget, so a hub that stops answering in the middle of one is noticed when that request gives up. A hub that answers within the deadline stays online however busy.
- While the hub is known unavailable, a desktop replica answers restore, select, conflict choice and backup acknowledgement with 503 "Hub unavailable. Try again when it is reachable."; otherwise those calls use 10 seconds (25 for restore and conflict choice) and no longer hold the local queue during hub I/O. Body-read drops and gateway answers count as unavailable, remote views never decide connectivity, and the snapshot session is released in a `finally`. The desktop and web interface show Restore, Resolve conflict, Choose folders and Select, gallery Delete and Disconnect… disabled with "Needs the hub, which is unavailable." and a guarded action sends nothing; a hub-only failure reads "This needs <hub>. Try again when it is reachable." and never claims edits were saved locally.
- Offline, replicas keep local browsing, gallery listing and photo metadata, local rename and delete, all of which show what changed on this device's disk at once, not at the next sync; historical restore and administration need the hub. The known catalog comes from synchronized configuration without waiting for the hub. Machine and history reads use a three-second deadline (once one has timed out the next ones answer from saved data for twelve seconds or until a cycle finds the hub reachable, so a hub that accepts connections and never answers costs one deadline, not one per view) and persistent caches scoped by hub identity (recent history metadata for up to 50 entries per selected folder for each of revisions, deleted and conflicts, refreshed on index changes, retention or conflict changes, or hourly). Cached information is marked as saved, never current hub authority, and never includes historical file contents. History takes its folder list from the saved catalog (a folder the hub answers 404 for contributes no rows; selecting a folder adds it to the saved catalog at once, so a folder selected while paused appears in History before the next cycle) and reads every folder's page in parallel under the same 3-second view deadline (`packages/core/scoped-activity.js`, shared with phones). Offline file history uses the saved folder history rows for that path, else the local row, and prefers a newer local row; a preview of a retained revision answers 503 at once while the hub is known unavailable and gives up after 3 seconds otherwise; desktop and server replicas save machine information after successful syncs, at most once a minute. Interrupted pending changes replay at cycle start before any hub call.

### Exclusion policy

Each share has one root `.arcaignore` for its own rules. Creating a hub folder always writes the rule-free [default.arcaignore](packages/daemon/default.arcaignore) (two comment lines with examples) unless one exists. Replicas never seed it and scans never recreate a deleted one; a missing file is fine and the hub's `.arcaignore…` editor creates it on save. Missing or empty rules mean no user exclusions; the fixed list still applies. Nested `.arcaignore` files are ordinary content, and `.gitignore` is never read.

The fixed list in `packages/core/builtin-exclusions.js` always applies on the hub, desktop and mobile, with or without `.arcaignore`, and `!` rules cannot re-include it. It matches case-insensitive names at any depth: OS metadata (`.DS_Store`, `.localized`, `._*`, `Icon\r`, `Thumbs.db`, `ehthumbs.db`, `desktop.ini`, `.directory`), OS and volume folders (`.AppleDouble`, `.Spotlight-V100`, `.fseventsd`, `.DocumentRevisions-V100`, `.TemporaryItems`, `System Volume Information`, `lost+found`, `.fuse_hidden*`, `.nfs*`), trash (`.Trash`, `.Trash-*`, `.Trashes`, `$RECYCLE.BIN`, `#recycle`, `@Recycle`), NAS thumbnails and snapshots (`@eaDir`, `#snapshot`, `.@__thumb`), other sync tools (`.stfolder`, `.stversions`, `.dropbox`, `.dropbox.attr`, `.dropbox.cache`, `.sync_*.db*`), temporaries and locks (`*.tmp`, `~$*`, `.~lock.*#`, `*.swp`, `*.swo`, `*~`, `.#*`, `#*#`, `*.crdownload`, `*.part`, `*.partial`, `*.download`, `*.pid`), regenerable caches (`.git`, `node_modules`, `.venv`, `__pycache__`, `*.pyc`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.tox`, `.cache`, `.gradle`, `.m2/repository`, `.next`, `.nuxt`, `.svelte-kit`, `.turbo`, `.parcel-cache`, `.expo`, `.dart_tool`, `.terraform`) and `.obsidian`. Names that may be content never join it: `cache/`, `build/`, `dist/`, `target/`, `out/`, `logs/`, `*.log`, `*.lock`, `.env`, SQLite files, `.idea/`, `.vscode/`, `venv/`, `env/`, `vendor/`, `Pods/`; `.gitignore`, `.gitattributes` and `.github/` synchronize.

- Skipping these names before validation also keeps unrepresentable (`Icon\r`), unreadable (volume folders) and symlink-bearing (`.venv`, `node_modules/.bin`) paths from stopping a scan. Directories are excluded before traversal.
- Only OS metadata is disposable: deleting an unlinked copy removes a folder left with only such files, never one holding temporaries, caches or `.git`, and never one that has become a link or sits behind a linked ancestor (the cleanup checks that each planned directory is a real directory at its own path before reading and again before deleting). Backup recovery never writes fixed-excluded paths.
- **Excluded paths are outside Arca.** Whenever a folder's policy key changes (its `.arcaignore` text plus the `FIXED_POLICY` fingerprint of the fixed list, stored in `sync_state.policy` or the phone's settings), the hub, desktop replicas and phones forget matching index rows. The hub records when each path with history was forgotten (`forgotten` table) and retention ages those revisions out from that moment as if deleted: Off at the next pass, Forever never, with the backup floor, pins and snapshot leases still applying before objects are collected. Hub proposals and forgetting evaluate the same policy (`visibleRules`, including catalog-only folders). Files on disk are never touched and no deletion propagates. Re-including a path imports it again from disk: identical replica content is adopted, different content becomes a conflict copy. A tombstone forgotten with its path is not replayed, so re-inclusion can bring back a file a replica never saw deleted.
- A hub rejects proposals for fixed-excluded paths, which stops a whole folder on an older replica that still proposes them, while a newer replica simply stops proposing them to an older hub; deploy replicas first.

Rules use [node-ignore's gitignore semantics](https://github.com/kaelzhang/node-ignore) with **case-insensitive matching**: `*`, `**`, `?`, character classes, `#` comments, escaped leading `#` and `!`, leading `/`, directory-only trailing `/` and `!` exceptions. Later rules win, subject to excluded parents: `!cache/file` cannot restore a file while `cache/` itself is excluded; use `cache/*` for selective exceptions.

```gitignore
# Ignore temporary files anywhere
*.tmp

# Root-relative folder
/build/

# Logs at any depth
**/logs/

# Keep one file inside a partially excluded directory
cache/*
!cache/keep.json
```

- The root `.arcaignore` synchronizes and is versioned even if a broad pattern would match it. It must be a regular file of at most 64 KiB; unreadable, oversized or symlinked rule files stop the affected operation instead of treating the share as unrestricted.
- The hub's policy is edited through `GET /v1/ignore-policy?id=ID` and `POST /v1/ignore-policy {id,text,version}` on an active hub working copy: at most 64 KiB, saved as a normal revision, stale editor versions rejected, absent files created only on save, empty text meaning no user exclusions. These endpoints never give linked credentials hub administration.
- A replica fetches accepted hub rules before scanning. Different custom rules on first link, or concurrent edits, stop ordinary transfers until both sides agree; stale policy proposals are rejected without a conflict copy. Local rule edits are proposed before ordinary files. Rules are checked on scanning, proposals, incoming materialization and missing-file deletion checks, and changes need no restart.
- Ignoring a file never deletes it on disk and never proposes a tombstone; a newly included file joins two-way sync on the next cycle, and editing rules never overwrites existing contents.

#### The maintainer's `~/.alpi` policy

`~/.alpi/.arcaignore` follows that folder's `.gitignore` **except that `.env` and secrets are intentionally included**. It was copied and adapted by hand, because Arca never reads `.gitignore`; broad exclusions need parent directories re-included before child exceptions. It is user content: read the active file before editing it, and never restore older credential-excluding versions. Never put secret contents in logs, docs, screenshots or fixtures. It is not a transactional backup of running application databases.

### Local metadata and previews

`.arca-volume` identifies a local working-copy registration and is not user content; unlink removes a matching marker. A destination preview counts eligible file metadata after `.arcaignore` filtering without hashing, reading contents, following symlinks or creating files, bounded to 100,000 visited entries or five seconds; an incomplete count is reported as unavailable, never as a total or a transfer size.

## 4. Desktop, server and web

Desktop and web share `apps/desktop/src`. Tauri (`apps/desktop/src-tauri/src/main.rs`) adds the native bridge, window lifecycle, tray, onboarding, folder picker, notifications, clipboard and launch at login (macOS only); none of these ever exposes credentials to frontend JavaScript. The daemon ships inside the app as a bundled official Node runtime with FFmpeg, Sharp, exifr and music-metadata.

### App lifecycle

- Closing the window hides it; Quit exits the UI and leaves the separately spawned daemon running. The daemon owns watchers, hub event listening, bounded requests and retries independently of UI focus. System sleep suspends work until wake; there is no keep-awake override.
- The main window zooms with Command +/−/0 on macOS and Control +/−/0 elsewhere, 70–150% in 10% steps, persisted locally; tray sizing and browser zoom are separate.
- The Tauri window maps a daemon-unavailable error to the Service stopped page, probes every five seconds and clears stale notices on recovery; the tray offers Start service.
- Folder lists render local status at once and refresh the remote catalog in the background, keeping the last known catalog on failure; an unavailable hub never leaves the desktop on its startup placeholder.
- Main-view navigation paints current data before waiting on API reads. Status refresh runs alongside view reads, discovery and roster load concurrently, and equal pending reads are shared. History keeps up to 20 first-page snapshots keyed by daemon, hub, filter and path, cleared at sign-in boundaries. Folder activity and browse responses (up to 100) are kept in session memory per machine, hub and exact route, so a known folder renders at once while current data loads, and a failed refresh keeps it. Old route responses never replace a newer view. Navigation, reads and folder or history actions bypass the mutation queue; mutations are serialized without dropping distinct clicks.
- Background polls never own the foreground action lock and never overlap. They patch counts, progress and completion text in place, defer structural repaints while a pointer is pressed or an input, menu or dialog is active, restore scroll and focus when a repaint is unavoidable, and scope folder-detail refreshes to the selected folder. Folder-detail file counts still invalidate listings so new and deleted files appear.
- Web admin requests time out (events 25 s, reads 20 s, writes 30 s, gallery and discovery 65 s; unlink, move, promote and destroy unbounded). Browser transport failures show an actionable connection message. An interrupted GET retries once; a mutation or a single-use login is never replayed. The file page sends the newest known revision for rename and delete.

### Desktop updates

The packaged app updates itself. `tauri-plugin-updater` reads a rolling manifest at `releases/download/desktop-latest/latest.json` and verifies every payload against the minisign public key embedded in `tauri.conf.json`; an unsigned or mis-signed payload is refused before anything is written. The private key lives only in the `TAURI_SIGNING_PRIVATE_KEY` repository secret and on the maintainer's machine.

- **Daemon coordination.** The daemon runs the bundled runtime from inside the installation being replaced, so leaving it alive would lock `node.exe` on Windows and keep old code serving an updated window. The payload is downloaded and verified while the daemon keeps syncing; only then is it stopped. A daemon is stopped only when its lock names a live process whose command line runs `arca.js daemon` and ends with `--home` for this state directory, so a stale lock never kills a reused PID or another instance. An unreadable lock or process listing, or a daemon that answers without being identified, refuses the update. On macOS a loaded Launch at login agent is booted out first so launchd's KeepAlive cannot respawn old files; Windows ends the daemon forcefully because a windowless process never receives a close request.
- **Restoring the daemon.** Before stopping, a marker records how to bring the daemon back (login agent or direct spawn); it is removed only once the daemon answers again. A failed stop, or an install that fails while Arca runs, restores the daemon immediately; a successful install restores it on the next launch from the new files. On Windows the plugin hands the payload to NSIS (`/P /UPDATE /R`) and exits, and NSIS relaunches Arca only after success; when a daemon was running, Arca first starts a detached watcher (`packages/cli/update-watch.js`, run by a copy of the bundled Node in a temporary directory because NSIS replaces the installation's files). After Arca exits (or its image is gone, so a reused process id never stalls it) it waits while the installer the plugin writes, `<productName>-<version>-installer.exe`, is running (at most ten minutes); if the marker is still there and Arca has not relaunched after 45 quiet seconds, it starts the daemon directly unless one already answers, and clears the marker once the daemon answers (`start-failed`, also when the daemon cannot even be spawned, keeps it for the next launch). It records its outcome in `update-watch.log` in the state directory, removes its temporary copy and is cancelled when the install fails while Arca runs; Arca also sweeps leftover `arca-update-watch-*` directories when it opens. If the watcher cannot start, the daemon stays stopped until Arca opens again and the marker restores it. The per-user installer needs no elevation. If the restart fails, the marker stays for the next launch and the Service stopped page shows the reason beside Start service. With no daemon running there is no marker, so an update never starts a daemon the user stopped. Sync pauses from the stop until the updated daemon answers.
- **UI.** `check_update` and `install_update` are ordinary Rust commands, so the browser build never updates itself and no updater permission crosses IPC. Checks run at startup, every six hours and on reconnect, silently on failure. The sidebar shows a compact card only when an update exists: neutral border like the sync card, "Arca {version} is available" and a small secondary "Update and restart" button; a failed install re-enables it and reports through the usual notice.
- **Artifacts.** `createUpdaterArtifacts` signs a payload per platform: `.app.tar.gz` on macOS, and the NSIS installer, AppImage and Debian package elsewhere, each with its `.sig`. A missing signature means signing broke for the whole release, and `collect-release.js` fails the desktop job before publication. After the release is published, the `updater` job builds `latest.json` from the four signatures and moves the `desktop-latest` tag to the same commit. The plugin reads `{os}-{arch}-{installer}` before `{os}-{arch}`, so Debian installations get `linux-x86_64-deb`. `updater-manifest.js` refuses a manifest missing any platform. The app reports its version only through `APP_VERSION` in `apps/desktop/src/app.js`, which `check-release.js` validates.
- `tests/update-watch.test.js` simulates the watcher with a fake clock and with real processes (a failed installer, a relaunch). Rust unit tests in `apps/desktop/src-tauri` (`cargo test`) cover daemon identity (this state directory only, quoted Windows paths, other homes and commands rejected), failed process listings never counting as stopped, stale, foreign and live locks, and tray assets and states; the `rust-tests` job runs them in CI. The update install flow itself (`install_update`, stopping and restoring the daemon) has no Rust test.

### Gallery

A folder becomes a gallery through the persistent `gallery_folders` marker, set by a phone linking an album (`/v1/gallery/link`, advertised as `gallery`) or by Enable gallery in the hub's ordinary folder detail; desktop and server replicas never offer it and their daemon answers `/v1/gallery/link` with 409 like any hub-only route. The marker is in the catalog and status and cached by replicas. It changes nothing about sync, originals, unlink or deletion, and unlinking the phone keeps the presentation. Gallery contents follow the current index and ignore policy.

- **Timeline.** `GET /v1/gallery` returns items newest first by capture date, then filename, album folder and date added, grouped by calendar month, with keyset pages of sixty (`before=` with a `previous` cursor seeks a month and loads newer items above it; `from=` keeps refreshes on the same range). Photos and videos share one chronology. The per-month timeline carries each month's count, `videos` count and newest revision, and `undated` carries the count, the video count and the newest revision of the items that have no date at all, so the desktop header and the phone gallery total count every photo and video and the phone reloads the Undated group when either the count or that revision changes, even when a photo is replaced by another and the count stays the same. Listing never waits for metadata: it returns files with fallback dates at once, indexes in the background and exposes `indexing` so the UI can refresh dates when ready.
- **Dates.** Validated phone capture timestamps sent with proposals are authoritative. Otherwise images read DateTimeOriginal, CreateDate or ModifyDate from bounded EXIF, and videos read container tags (QuickTime creation date, then `creation_time`/`date`) with the bundled FFmpeg without decoding frames (15-second timeout, 1 MiB output). Offset-bearing times normalize to UTC; offset-free EXIF keeps the camera's date; phone timestamps use UTC days. Fallbacks, in order: recognized dated filenames and the phone's year/month path (`packages/core/gallery-date.js`, month precision for paths), the earliest file modification time a desktop or server replica reported with a proposal (labelled File date), then the first accepted revision date (date added). Malformed file times are ignored. Metadata is content-addressed in `gallery_metadata` and indexed in batches of 64; unsupported media are marked checked so indexing ends. The hub attaches each media file's recorded date to snapshot and change rows, so replicas date undated photos like the hub, offline too.
- **Derivatives.** Sharp renders auto-oriented JPEGs at 360 px (thumbnail) and 2048 px (large), with 100-megapixel input limits and a ten-second decode timeout; HEIC and HEIF decode through pinned libheif-js 1.23.2 WebAssembly in a worker (20-second timeout, 128 MiB input, 100 megapixels), independent of Sharp's HEVC support; the runtime ships its upstream LGPL licence files and replaceable module and wasm files, with sources at https://github.com/catdad-experiments/libheif-js/tree/v1.23.2. Derivatives live in a private `previews` directory tracked in `gallery_derivatives` with separate budgets: every photo keeps a thumbnail (1 GiB safety cap), generated for the whole folder before any large preview, and large previews keep a 512 MiB LRU budget, prepared newest first until 90% full, the rest on demand; a large preview evicts only large previews. The in-memory cache holds 32 MiB, concurrent requests share work and preparation runs at most four jobs. Accepted uploads and completed replica syncs enqueue preparation without delaying acceptance; preparation walks marked galleries in bounded batches, resumes on startup with a hash-keyed ledger, and retries unavailable originals after 24 hours or on demand. Originals and objects are never modified; library conversion does not exist.
- **Replicas show only their own files.** Desktop and server replicas render previews, metadata and video from their working files (by scan signature, else a size check). They never ask the hub for the pixels of a current file: one not held yet answers 409 "Sync this photo before previewing it" and stays a placeholder. A `?rev=` preview of the revision the replica holds renders locally; only other retained revisions come from the hub, with a 3-second cap (15 seconds for `size=large`); a hub that does not answer in time while it is not known to be down answers 504 "The hub took too long to prepare this preview", never "Hub unavailable", which stays for a hub already marked unreachable or refusing connections; the desktop row of an older version whose preview failed this way keeps its placeholder and shows a clock in the status corner whose tooltip and accessible label (an image role) carry that answer; this is the desktop app only, because the browser client turns every 502, 503 or 504 on a GET into its generic "cannot reach this device" error and keeps the plain tile. Selected replicas serve gallery listings and Info locally; disconnected replicas render local images with local EXIF dates.
- **Access.** Preview and list endpoints require authentication and check the current path, hash and exclusion policy even on cache hits. Large previews are binary JPEG; thumbnails use the JSON bridge. Browser requests use the session; native images and video use random, two-hour, loopback-only tickets scoped to one current file and hash (at most 32), restricted by origin, revision, exclusions and selection, so no bearer credential enters a URL. The desktop CSP allows loopback images only. `GET /v1/gallery/preview` accepts a positive `rev`, validated against retained history before touching the cache; browse file rows include their hash.
- **Video.** The viewer uses a real video element with authenticated single-range GET/HEAD streaming from verified immutable content, rechecking visibility and selection per request; playback relies on browser and OS codecs, with original download otherwise. Posters are one JPEG frame extracted by a bounded FFmpeg process (15 seconds, one thread, 8 MiB output, explicit container, local-file input only) for MP4, MOV, M4V and WebM, cached like other derivatives.
- **Downloads** stream authenticated current originals through `/v1/gallery/download`, rejecting stale, deleted, excluded and unselected files. Native desktop saves through a system Save dialog with root containment and same-path checks.
- **Info** (`GET /v1/gallery/info`) reads metadata on demand with the same routing and checks: orientation-aware dimensions and megapixels, make and model, lens, aperture, exposure, ISO, focal length, capture time with its offset and GPS. Missing fields are omitted, nothing is written back and no geocoding service is called. It reports whether the file has another retained revision and the accepting revision; a machine name appears only when resolved from hub records.
- **Deletion** uses the shared confirmation and the revision-checked `/v1/delete-file`, with partial-failure feedback and retry of the remaining files, and propagates through ordinary sync. After success the tile is removed and its row reflowed without refetching; a local visibility marker keyed by machine, hub, folder, path and deleted revision filters cached and fresh pages so a replica's not-yet-synced deletion cannot reappear, while newer revisions (a restore) stay visible. Recovery depends on folder retention.
- **Caches.** The session keeps at most 64 MiB of encoded previews (48 MiB and up to 2,000 thumbnails, 16 MiB and up to eight large previews, keyed by hub, volume, path, hash and size, LRU) and up to 40 completed gallery pages, refreshed in the background after 15 seconds. IndexedDB stores gallery pages and thumbnails per machine and hub, at most 128 records of 300,000 serialized characters, never tickets or originals; mutations invalidate stored pages and sign-out clears them. An open gallery rechecks its loaded range every five seconds while visible (not while the viewer or a selection is active), reconciling without losing the visible anchor.
- **Images settings** (hub administrators, desktop hub and server web) count current visible images and videos in gallery folders with their logical sizes, and Regenerate previews rebuilds derivatives in the background: one job per hub, Stop process between files, not resumed after restart.

### Music libraries

A folder becomes a music library through the persistent `music_folders` marker, set only by a hub administrator with Enable music library in the hub's Folder actions menu (`POST /v1/music/mark`; 409 on replicas, on a gallery folder, and `/v1/gallery/link` answers 409 on a music library). The marker is in the catalog (`music` per folder, and `music: true` as the capability) and status, cached by replicas, survives restarts and goes with Delete shared folder. It changes nothing about sync, selection, unlink or deletion. There is no Disable, as for galleries.

- **Index.** The hub reads tags with `music-metadata` from its own content objects, and a desktop or server replica from its local copy of the music folders it selected, for `mp3`, `m4a`, `aac`, `flac`, `wav`, `ogg`, `oga` and `opus` files into `music_tracks`, keyed by content hash, so renames and copies never re-read a file: title, artist, album artist, album, track and disc numbers, year, the first genre, duration from headers, codec, the MusicBrainz release id (`release`, kept only when it is a UUID and lowercased) and the cover key; a change of what is read bumps the index version, so the hub, and a replica for its own index, reads existing tags again once. Only visible current files are read; excluded ones never are. A file that cannot be parsed, or takes more than 30 seconds, keeps an empty row and is listed by its name; content the hub cannot read right now (a missing content object, an I/O error, or a cover it cannot write) is tried again an hour later and does not hold `indexing` meanwhile; tags already read stay listed while a retry fails, and a re-read that times out or cannot parse a track that was read before keeps its tags and tries again an hour later. Indexing runs in the background in batches of 32, starts when a folder is marked, at startup, after a proposal touches an audio file and whenever a library read finds tracks not yet read or due again; a pass that read something advances the change feed, so replicas fetch the library again. A pass is skipped while the folder's files, the read tags and its exclusion rules are unchanged since the last pass caught up and no retry is due; a sweep that removes tag rows makes skipped folders read again. Tag rows and covers that no current file of a music library references are removed at most hourly after a pass, and at once by Delete shared folder, including covers that finish rendering after it.
- **Covers.** An embedded picture (at most 16 MiB) becomes a cover keyed by the SHA-256 of its bytes; a track without one uses the best `cover`, `folder`, `front` or `album` `.jpg`/`.jpeg`/`.png`/`.webp` of at most 32 MiB in its directory, else in the parent directory (album/CD1 layouts), keyed by that file's content hash. Sharp crops each cover to a centred square and renders JPEGs of at most 360 px (`small`) and 1024 px (`large`), never upscaled, into the private `music-covers` directory; a missing derivative is rendered again on request, and Erase removes the directory.
- **Library.** `GET /v1/music/library?volume=ID` (on the hub, with a linked replica credential or admin) lists the folder's visible current tracks with their tags, cover key and when that content first entered the folder (`added`, the oldest revision with that hash, so a move or rename keeps it), with `indexing` while some track is unread and a `version` hash of the tracks; `?version=` with the current value answers `{version, indexing, unchanged: true}`. Exclusions and deletions apply on every read; the answer is built again only when the folder's files, its exclusion rules or the read tags change. A desktop or server replica answers its administrator for a folder it selected from its own index; its tracks carry `added: null` because a replica keeps no revision dates.
- **Cover access.** `GET /v1/music/cover?volume=ID&key=…&size=small|large` returns `{data}` as a JPEG data URL only when a visible track of that library carries the key or a visible cover file of that library has that hash, `{retry: true}` when the cover could not be written for a transient reason (the hub renders that key again after ten minutes, and phones treat the pass as incomplete), and `{unavailable: true}` when that content cannot be read or rendered, without trying that key again for an hour; any other key is 404, a malformed key or size 400.
- **Playlists.** The library answer lists `playlists: [{path, name, hash, editable, entries}]` for the visible, current files directly under `Playlists/`, sorted by name: UTF-8 for `.m3u8`, UTF-8 else Latin-1 for `.m3u`, at most 1 MiB and 5,000 entries. `entries` are resolved folder-relative paths in file order, with duplicates and `null` for lines that do not resolve; `#PLAYLIST:` names the list, else the file name; `hash` is the content read (the hub's stored copy or a replica's working file), and `editable` is true for `.m3u8`. `version` covers playlists, and a changed playlist file refreshes the answer. The admin route `POST /v1/music/playlist {volume, action, path, name, track, position, hash}` creates, adds to, removes from, renames or deletes a playlist in this device's own copy of the folder through `packages/core/playlist.js`, writing atomically and only `.m3u8` files under `Playlists/`, then asks for a sync: 409 without a local copy, when the file exists on create, "This playlist changed. Try again." when `hash` or the removed position no longer matches, or "This track is already in this playlist." when an add names a track the playlist already lists (entries match by the folder path they resolve to, so another spelling of the same file counts); delete is the normal file deletion, so history keeps it, and rename moves the file through the local rename path and rewrites `#PLAYLIST:`, also when the file has edits that have not synced yet, which move with it. An edit changes only the entry it names and keeps every other line, including entries this device cannot resolve; a list made elsewhere keeps its repeated tracks, which play in order and are removed one appearance at a time. A file that is not valid UTF-8 or is over 1 MiB is read but never edited or rewritten (409), though it can still be deleted; a name that differs from an existing playlist only by case is refused; a replica also lists the `Playlists/` files it holds before they have synced. Renaming or moving a file of a music library through Arca rewrites the editable playlists that name it in the same operation.
- **Desktop and web.** Music folders show the music tile in Folders and in their header, and offer neither Enable gallery nor Enable music library. A music folder opens on its library on the hub and on a desktop or server replica that selected it, and enabling a library opens it; View folder switches to Files and Recent with the stats and side column and reads Library to come back. The library comes from the daemon being managed: the web admin and a desktop hub read the hub, a replica its own index, which it builds at startup, after each completed folder sync and on library reads, and whose sweep keeps its own tags and covers. The tabs, grouping and sorting follow the phone's rules; `apps/desktop/src/music-library.js` mirrors `apps/mobile/src/music-library.js`, and a test keeps both in step.
- **Desktop and web playback.** One `<audio>` element plays over authenticated single-range streaming. A browser session plays the same-origin `/v1/music/media?volume&path&hash`; the desktop app asks `/v1/music/playback` for a two-hour, loopback-only ticket (at most 32, kept apart from gallery tickets, with the same origin allow-list) for one current, visible audio file of a music library whose local content has the recorded hash and size. Other files, folders or stale hashes answer 404, an unselected replica folder or a linked credential 403, and a missing or changed local copy 409 "Sync this track before playing it", so a desktop replica plays its own copy, offline too. A library opens on Artists, with tabs Artists, Albums, Playlists (once a playlist exists) and Recent; Artists is the A–Z index of the phone's order, 120 artists at a time with Show more. Every track row ends in a ⋯ menu with Add to playlist… (a picker of editable playlists and New playlist…) where this device holds the folder and, on an editable playlist's page, Remove from playlist; a playlist page reads as an album page, with Rename… and Delete playlist… for editable files. Entries that do not resolve are dimmed and never play: "Not on this device yet" on a replica still syncing the folder, else "Not in this folder". Playing a playlist queues its resolved tracks in order with duplicates, each appearance marked by its position. Tapping a track queues its album from that track; Shuffle on an album plays it in shuffled order from a random track; repeat cycles off, all and one. Recent keeps this device's last 20 played albums and playlists, newest first, in local storage keyed by hub and folder, and never sends them to the hub; renaming a playlist moves its entry to the new file; until something plays it shows Recently added with a caption, or Nothing played yet when no track is dated. When `navigator.mediaSession` exists it gets the title, artist, album and cover and play, pause, previous and next handlers, so browser media keys work. An open library that is still indexing reads again every five seconds, per folder, also after a failed read. Every album tile and album or artist header uses one cover size, 160px (120px under 760px), in fixed left-aligned columns. The Search button at the end of the tabs row opens the Files search field; while it holds text, results replace the tab in groups shown only with matches: Songs (title, artist · album and duration, 120 at a time with Show more songs; a song plays within its album from that song), Albums (the grid, 60 at a time), Artists and Playlists (rows, 120 at a time), each with Show more. Matching is a case-insensitive substring of title, artist, album artist, album or playlist name that ignores combining accents (U+0300–U+036F after NFD, the same folding as the phone), and a query that is empty after folding and trimming shows the tab; no match reads "No results for “query”", and Escape or an empty field returns to the tab. The query belongs to the open folder and is never stored. Shuffle beside the tabs appears only at a tab root (the Artists, Albums or Recent list), not on artist or album pages, which have their own Shuffle, nor while search results show; it plays every track in the library shuffled from a random track, and an artist page heads with the artist's cover, name, "N albums · N tracks" and Shuffle for all the artist's tracks; neither enters Recent. A track that fails before its metadata loads keeps its last position and Play resumes there, and a library read already in flight is shared, so Play waits for it. When the library changes, the play queue follows it by path: tracks take their current hash and removed tracks leave the queue, except the one playing. The desktop app renews a lost or expired ticket once per track and resumes at the same position; a second failure reads "This track cannot play here. Its format may not be supported." for unsupported or undecodable media and "Playback was interrupted. Press Play to continue." otherwise, and Play resumes where it stopped. The player stops, unloads its audio and clears the media session and the music caches when the browser session ends, the device returns to onboarding, the managed hub changes, or the playing folder is no longer a library this device can play (Delete shared folder, Stop syncing). While a track is loaded, the full player bar shows in the library view of any music folder; every other page shows a compact card in the sidebar directly above the status card (below Update available), whose cover, title and artist form one button that opens the playing album in its folder's library, with Play/Pause and Next. In the bar the cover and title do the same, and the second line's artist and album open the artist page (the track's artist when the library has one, else the album's artist) and the album, from any folder, tab or search; each moves focus to the bar's Play/Pause. Under 761px the card hides and the bar shows on every page; both leave when the player stops. In the desktop app the tray popover shows Now playing between the status header and the folders while a track is loaded: cover, title and "artist · album", Previous, Play/Pause and Next, which act on the main window's player without showing it, and the track brings the window forward on the playing album and closes the popover. The window publishes `music-state` (title, artist, album, folder, cover key, whether it plays and whether Next is available, or null after a stop) once per track or play-state change, never while a track loads, on request and `null` on startup; the popover asks again on focus, patches its box in place, and retries a failed cover a minute later with at most two cached; and takes `music-command` (state, toggle, next, previous, show) over the Tauri event bridge; Quit Arca stops the music and the daemon keeps running.

## 5. Mobile

The phone and Fold app (`apps/mobile`) is an Expo/React Native JavaScript replica with a transport free of Node dependencies, hub identity pinning, SecureStore credentials (Keychain or Keystore-backed; never described as the Secure Enclave), a local SQLite index and persistent transfer state. Files live in persistent app documents storage, not purgeable caches; external Files integrations depend on platform permissions, and iOS never promises desktop-style paths. It is never a continuously running daemon.

### Platform and native module

- Expo SDK **57.0.24**, React Native **0.86.3**, React **19.2.3**; iOS 16.4 minimum (`ArcaNetwork.podspec`). `expo-file-system` `copy()` and `move()` are awaited; paginated media-library calls come from `expo-media-library/legacy` through `media-library.js`. React Native 0.86 has only `StyleSheet.absoluteFill`, and the text-scaling pass skips anything that is not a style object so a future removal degrades instead of crashing at launch.
- The local `ArcaNetwork` module (Kotlin and Swift) is required directly, with no optional-module fallback. It provides network requests whose block transfers read and write app-owned temporary files with range and length validation and no payload base64 across the bridge; streaming SHA-256 on Android; `replaceFile` (fsync the source, then an atomic rename; iOS also fsyncs the parent directory and raises every failed open or flush, so a failure before the rename leaves the destination untouched and the phone keeps its recovery record, and a retry completes the replacement); `receiveShared` (Android, `SharedFiles.kt`: copies a shared `content://` file into the private inbox under a generated name); gallery export (`GalleryExport.kt`, `GalleryExport.swift`); thumbnails (`ArcaNetwork.thumbnail(source, destination, size, cover, video)` in `Thumbnails.kt` and `Thumbnails.swift`); non-recursive `removeEmptyDirectory`; opening files (Android `ACTION_VIEW` with a temporary read-only content URI, iOS Open In); APK installation (`REQUEST_INSTALL_PACKAGES` with the APK MIME type, explaining and opening settings only on an explicit tap); the Android transfer session; and the clipboard. Android network, hashing and export run on coroutines on `Dispatchers.IO`; iOS uses async URLSession. Metro cannot add native methods: native changes need a new binary.

### Replica cycle

- Each selected folder runs push, then album uploads in their own turn, then pull. A yielded or failing upload pass still reaches the download; only an interruption or an unreachable hub skips it. Initialized folders sync before first-time folders. Each failed folder records its issue and the rest continue; a connection loss stops the cycle without marking every folder failed, and offline state stays visible during retries.
- **First snapshot.** It resumes from a saved lease, page position, cursor and deferred rows (setting `snapshot:<scope>:<folder>`) across yielded turns, `stop()` interruptions (pause, file operations, background expiry, Android service stop) and unreachable-hub errors. Completion, `resetCursor`, folder removal or any other failure clears it; an expired lease restarts it once. `apply()` skips rows older than the local revision, so a resumed snapshot cannot roll back rows pushed between turns. Leases are released through the interactive client with a three-second deadline, even after sync stopped; 429 and 409 waits are not folder failures. Continuation turns still repeat the catalog, policy check and the 60-second local scan.
- **Turns.** Transfers yield after ten seconds per folder, continue other folders and resume from durable offsets without recording an error. Slow local preparation does not consume the first turn. Scanning and native export are not preempted.
- **Verification.** Hash, size and mtime survive cold starts in SQLite. Full verification runs hourly and on forced sync, tracks unfinished folders across turns and bypasses the hash cache while continuing; a folder that failed or was skipped in the cycle does not hold the verification time back, so healthy folders are not re-hashed every sync because one folder keeps failing; that folder gets its cache-bypassing hash at the first hourly or Sync now verification after it recovers. Scheduled cycles reuse a local inventory for up to one minute when nothing is pending; resume and Sync now inventory at once. `apply()` verifies existing files with the same size/mtime-checked cache. Materialization hashes local content before replacing it, deletion hashes the file, and queued operations are recomputed after a complete inventory. Pending uploads are not re-hashed every turn: an unchanged queued object is verified once per app session and again after the hub rejects it.
- **Conflicting proposals.** When the hub answers a proposal with a conflict, the phone stores the hub's newer row marked `unapplied` (with the proposed content as its `localHash`, the baseline for safe materialization) and its scan proposes nothing for that path, a missing file included, until a pull applies the row; so a cycle that stops between the two (offline, the app killed, Rename, a playlist edit or Delete interrupting it) never proposes the phone's version, or its deletion, again on top of the other device's newer one. The phone's own content survives as the hub's conflict copy, and the pull keeps any later local edit as a `.conflict-mobile-` copy.
- **Pull.** One lazy case-folded path index per pull checks case aliases and updates as rows apply (tombstones and same-pass renames included). Matching accepted revisions still verify local bytes without rewriting their journal. Downloads use sequential 1 MiB blocks, and materialization copies the verified object into the working folder.
- **Storage.** Objects hold only transfers in flight: `transferHashes` is pending uploads plus rows being applied. `cleanTransferObjects` runs after every successful cycle, before folder errors are raised, and removes every other object, so a downloaded file exists once. Explicit folder removal reclaims unreferenced objects and keeps those that other folders, pending operations or recovery journals reference.
- **Machine reports** use folder aggregate counts, are published right after the catalog refresh (before long transfers) and again at completion. A machine rename goes through the interactive client, is validated (1–100 characters, no control characters), saved locally and published through the report; offline failures keep the name for the next sync.

### Requests and cancellation

- Deadlines cover response bodies as well as headers; cancelling after headers interrupts stalled reads, and cancelling an unfinished authorization keeps the saved connection. Upload and download blocks get 15 seconds plus one second per 32 KiB; buffered native bodies are never timed out after arrival. Concurrent catalog refreshes share one request with a 10-second deadline, which is also how long a first cycle takes to call a silent hub offline. A caller that stops waiting (rename, delete, import, pause) never aborts it and its answer is recorded as the connection verdict when it settles; destroy, disconnect, pairing, backgrounding the app and a platform time limit cancel it, and a pending disconnect's leave request shares its deadline. A slow optional view serves saved data without marking the hub offline.
- Cancellation reasons survive React Native signals without `reason`, and native requests are cancelled explicitly. File-transfer cancellation waits for native completion before releasing the turn, so late writes never race resumed partial files. Replica requests carry their own signal while navigation uses the plain client; pause and Destroy cancel the replica scope and drain active work first. Late results after cancellation never update credentials or resume a cancelled sync.
- GET and HEAD retry once after 250 ms on unexpected EOF, connection reset or broken pipe; writes are never replayed after an ambiguous failure, and native reselection happens only before the request body is written. Persistent interruptions show an English connection error, never Expo or Java internals.
- LAN verification runs under the request's own abort and deadline, and its discovery probe is bounded to five seconds; only a parsed hub answer with `allowLanHttp !== true` asks for Allow HTTP. Native routing failures explain the Wi-Fi/Ethernet or Tailscale requirement and stop before any credential is sent. Discovery coalesces only overlapping requests and never caches a revoked opt-in.
- The phone unpairs only on 401; a 403 such as "Tailscale access unavailable" keeps the credential.

### Lifecycle and background

- Sync runs on launch, resume and through the explicitly enabled OS background task; background execution is opportunistic and OS-scheduled, never immediate. The event stream is used only in the foreground; healthy event delivery reduces periodic cycles to once a minute. iOS keeps syncing through `inactive`, stops on `background`, and background-task expiry stops sync. Cellular stays disabled for LAN HTTP only, never for Tailscale.
- **Android transfer session.** Foreground-started sync acquires `TransferSession` before catalog or file work, covering downloads, uploads and linked albums: a native `dataSync` foreground service with a Headless JS task that keeps timers alive, a bounded partial wake lock for screen-off work and an ongoing notification with current-file progress and Pause, which persists the ordinary replica pause. The session spans continuation turns and ends when the run ends, fails or pauses; Android timeouts and app termination stop it, leaving pending work resumable, and the timeout callback reports why. After an offline verdict (connection checked, hub unavailable) a cycle probes the catalog first and acquires the session only once the hub answers, so offline cycles never raise the notification or ask for its permission; a cycle whose catalog refresh fails releases it at once. OS-background runs never start it. No automatic restart, boot launch or battery exemption exists; Android 15's six-hour `dataSync` budget applies. Settings link to Android app settings with Samsung battery guidance.
- Runtime readiness is explicit state: Devices and automatic History wait for it and rerun when it arrives; unmounted startup work never publishes readiness. Startup clears persisted lifecycle-cancellation issues and keeps the last successful completion time; cached connection issues wait for the first connection check. A root error boundary shows Reload and Copy details instead of a blank app.
- **Actions.** Explicit actions use a foreground lifecycle: progress in the open sheet or a floating notice, no duplicate execution, a refresh and an exact retry on error; an error from the native layer shows its own message, with the module wrapper kept in Details. Manual Sync, Retry, selection-triggered sync and resume start the single-flight sync without holding the action lock, so navigation, Open, Share and list reads stay available during transfers. Rename, delete, import and playlist edits interrupt an active cycle and hold the action lock, so Erase this device is refused with "Wait for the current operation to finish." until they settle; the picker reserves the import batch before opening, so no automatic sync starts until the copy settles, and cancellation or errors release it. Export folder stops an active cycle and waits before the directory picker opens. Refresh notifications are throttled to 100 ms, storage snapshots coalesce into one active read plus one trailing refresh, equal snapshots keep React identity, free space is sampled at most every 30 seconds, and directory walks yield every 32 entries.
- **Crash record.** `src/crash.js` wraps the global JavaScript error handler before the app loads: a fatal uncaught error is written synchronously to `arca-crash.json` in app storage (name, message up to 600 characters, time) and the previous handler still runs; errors that did not close the app and render errors caught by the error boundary are not recorded. The next launch reads and deletes the record once and shows one persistent error notice, "Arca closed unexpectedly" with "Your files are safe. The error was saved on this phone.", whose Details hold the message and time and whose Copy puts them (secrets redacted) on the clipboard; nothing is sent anywhere. A corrupt record is discarded silently.
- **Offline.** Add files opens the picker without waiting for a cycle (on Android the picker hands over `content://` references and the native module's `receiveShared` copies each pick into the private `arca-incoming` inbox on an IO thread, so a large file never freezes the app; the inbox copies are removed after the import; iOS keeps the picker's own cache copy), copies each file through a hidden `.arca-copy-` staging file beside its destination (swept before the next import) and publishes it atomically inside the app's storage (a failed copy never removes or truncates what is there), treats identical bytes as nothing to do and puts different bytes under an occupied name at `<name>.conflict-import-<hash>` or the next free `-2` … `-99` path, so an edited conflict copy is never overwritten, and stops with an error when all hundred names are taken; Open and Share sit outside the action lock. Restore, Resolve conflict, Restore selected, Link album and shared gallery Delete (viewer and selection) are disabled while the hub is known unreachable, and Link album and Delete say "Needs the hub, which is unavailable."; hub-only failures use the notice wording "This needs <hub>. Try again when it is reachable."; Disconnect still works (the phone records it and leaves when the hub returns, with a "Disconnect pending" notice); a rename then saves locally and says so; when the hub comes back, Recent, Devices and an open file detail reload on their own (the detail refreshes without resetting, which re-enables Restore), and the saved-data captions follow each response's own `offline` flag; offline file detail leads with the phone's own version (marked Local copy, with the Current badge and its real version number) when the saved history lacks it or is older, and an empty saved window reads "No saved versions for this file."; with nothing saved the file detail, Recent ("No saved versions") and a photo folder without local files ("Nothing saved on this phone") each show the empty-state frame that says "You are offline" and ends in Retry, which probes the hub again and reloads the view, while a hub that answered empty shows the plain "No versions yet" and "No photos yet" frames, and a raw error never appears without Retry; Change album works offline; a never-uploaded file can be renamed offline using its local version. Add photos… on an album folder journals the picks as pending before contacting the hub, so offline they upload after reconnecting (also with automatic uploads off, since cycles still send picked photos) and the "saved locally" notice is true; a picked photo whose app copy is gone reports that it must be picked again or dismissed. Photo Info asks the hub only while it is reachable and otherwise shows the local copy's details. Folder Recent uses saved views, History refreshes when the hub returns, offline onboarding selects from the saved catalog, and picker cache copies are deleted after import.
- **Saved views.** Devices and History use a persistent hub-scoped SQLite cache of 64 responses. Successful sync prepares machine information and up to 50 recent metadata entries per selected folder and filter, with a shared three-second optional-work deadline and a one-minute freshness window. Devices go first, then the pages that are missing or stalest, every folder's revisions page before the rest, four requests at a time, so a slow hub still gives each folder a saved page within a cycle or two. Saved data never enables offline hub mutations or historical downloads, is marked as saved, and never replaces an access or revocation error. Retention changes invalidate that folder's pages, removing a selection removes its views, and destruction clears the cache.

### Folders on the phone

- **Selection** explains the space and full-copy behavior and preflights free space. The last completed sync belongs to the current hub.
- **Stop syncing…** removes the app-owned working directory, its index and queued changes after a confirmation titled with the folder name ("Stop syncing “name”?", button "Stop syncing and delete") saying that unsynced changes are lost (pointing to Export folder); album-linked folders also state that Photos originals and uploaded hub files stay. It stops the active sync, persists the removal intent and works offline, with pending edits or after the hub deleted the share. An interrupted deletion keeps a durable `removing:` marker that skips the folder in every cycle and blocks reselecting it, shows Needs attention and retries. Pause and Disconnect keep local files. A share missing from the hub catalog keeps its index and reports an actionable issue; history reads intersect selections with the catalog.
- **Export folder…** copies the local folder outside Arca without sync or history.
- The open folder refreshes after automatic sync finishes, and an older asynchronous listing never overwrites a newer navigation. Local explorers keep bounded per-hub caches (20 folder listings, 40 Recent pages) while filesystem reads run.
- Replica History is scoped to selected folders (paused included); unselected file history is rejected, and aggregate activity merges selected volumes' revision cursors before pagination, as on desktop replicas.

### Linked albums

Linking an album adds automatic original-resource uploads to ordinary two-way sync of the folder; every participant keeps a complete copy.

- **Contract.** Linking preserves the existing Arca copy, including excluded and unsynced content, and never removes local content. Incoming files from other participants stay in Arca storage and are never imported into Photos. Removing a photo from Photos never deletes its accepted shared copy, and Arca never removes Photos originals. Shared edits and explicit deletions synchronize to every Arca copy. Changes in Photos create revisions with ordinary conflict protection, and a remote deletion suppresses automatic re-upload. Disabling uploads stops only album discovery and exports; album permission failures never block the folder download; an unavailable album keeps its upload warning without failing folder sync, and is never replaced or disabled automatically. Global pause and Disconnect stop both.
- **Interrupted conversions.** A folder left mid-way by the former upload-only conversion restores missing indexed files before scanning, so it cannot publish accidental deletions (ROADMAP DEC-CONVERTING-LEGACY).
- **Damaged records.** A gallery record that cannot be read as settings (invalid JSON, not an object, an unknown mode or a non-string prefix) reads as damaged (`parseGallery` in `validation.js`) and is never rewritten until repaired. The app keeps working, but that folder stops with "Photo uploads settings are damaged. Choose Change album… to repair them.": it is neither scanned, uploaded nor downloaded, and renaming or deleting its local files is refused, so a lost record can never publish deletions (an explicit shared-gallery deletion still applies on the hub). Change album… is enabled even with the default choices, asks the Enable photo uploads confirmation, turns uploads on and repairs the record through the interrupted-conversion recovery, restoring missing indexed files before the next scan; queued and failed uploads then retry.
- **Configuration.** Link album… chooses all accessible photos or any number of OS albums, optionally with videos; the source keeps the list as `albums` (`[{id,title}]`, empty meaning all accessible photos; a source saved with the former single `albumId` keeps that one album), discovery scans each selected album with its own cursor (`cursors`, cleared when a pass over every album finishes) and a photo that sits in several albums is one ledger row; an album that disappears is named in the issue while the others keep uploading, and only when every selected album is gone does the source report that the albums are unavailable (an unavailable selected album stays in the checklist, marked Unavailable, so it can be unticked); changing the selection is refused while uploads are pending, as for changing videos; editing an existing source keeps its enabled state. Records are scoped by hub and share (`gallery_sources`, `gallery_assets` in `replica-store.js`, with durable manifests, per-resource acceptance, retry timing and summaries). Stable resource paths use `Machine-<device-key>/year/month`. Reports list album-linked folders in both `folderIds` and `albumFolderIds` with real indexed totals, and folder UI reports local bytes, never upload receipts, as local content.
- **Runtime.** `gallery.js` owns source transitions, discovery, exclusions, uploads and receipt recovery. Each cycle discovers at most four 100-item pages and processes at most three queued assets; the cursor advances only after a whole page is inserted durably. Full scans repeat at most every minute, Sync now rescans, failed items back off for a minute and batches stop on connection loss without marking the rest failed. Native exports go to disposable private staging with bounded chunk writes, storage headroom and size limits and a 90-second timeout for iOS cloud requests and Android streams; low storage stops the batch after the first failure with a plain-language notice. Originals are hashed once after export; hub acceptance still checks the full hash. Uploads reuse chunk offsets and `/v1/propose`, and accepted uploads are also materialized into the working copy. There is no hub protocol for albums beyond the gallery marker.
- **Resources.** `GalleryExport.kt` reads MediaStore resources; `GalleryExport.swift` streams original PhotoKit photo, video, alternate-photo and paired-video resources, preferring full-size edited resources when available with stable role keys. Live Photo paired video is kept regardless of the video switch. Nothing is recompressed; album membership and edit databases are not exported, and OS metadata restrictions apply (such as Android's photo-location permission). Discovery tracks modification time, exports changed accepted assets, skips unchanged bytes and persists update manifests for retry; an editor that saves a separate asset produces a separate photo.
- **Receipts.** Lost receipts are recovered from per-path history before reacquiring an original, and an upload that was attempted but has no receipt also looks for the path's conflict copies in the folder's change feed from the resource's base revision (never a snapshot, whose first page would replace this phone's paused first-download lease) and checks their retained history, so a photo deleted from both phone and hub settles without resurrection (relying on retained hub history). `.arcaignore` applies to the working copy and album exports alike; excluded items stay explicit incomplete items and retry after a policy fix. Limited visibility never counts as full coverage. A library photo that disappears before it reaches the hub becomes `unavailable` once the export fails, the permission is full (never limited) and the library confirms the asset is gone (either its existence lookup says so, or the native export itself answers "Photo is no longer accessible. Check photo permissions.", which on Android and iOS with full access means the library has no record of it; a lookup that fails is never taken as proof on its own): it leaves the pending and failed counts, is not retried, never publishes a deletion and touches no hub copy or original, and returns to pending if an asset with the same id reappears in the album's scan or is picked again; an edited, already accepted photo deleted afterwards returns to accepted with the resources the hub holds. The same missing-asset check applies to manually picked library assets while automatic uploads are disabled. With limited access, denied permission or a lookup that cannot answer, the export keeps its retry. Item upload failures belong to Photo uploads, never to a second folder failure; identical notices are deduplicated, and a pass without new failures shows the latest failed photo's own reason.
- **One-time picks.** Add photos… (native picker) works in ordinary folders through the same receipt pipeline, obeys pause, journals all chosen items first and keeps going after one fails. Library IDs share the discovery ledger and exact hash and size receipts deduplicate later discoveries; a picked photo (one with no library ID) is copied into app-owned storage when it is journaled, so the OS clearing the picker cache or a changed container path cannot lose it (the journal keeps the pick's key and resolves the path under the current storage root each time); picking the same photo again reuses the copy, and one unreadable pick never stops the others being journaled; the copy is deleted once the hub has the photo. Picks upload before each cycle's library permission and album checks, so they still go when permission is revoked or the linked album is gone, and Sync now makes failed manual picks retry at once even with automatic uploads off. A pick whose app copy is gone stays failed with "Pick it again or dismiss it" and the Pending uploads header carries a Dismiss N action (a text link next to the remaining count, only while such photos exist) that retires only those rows, their tiles show the placeholder instead of an alert badge, and a line under the strip says how many are no longer on the phone and to pick them again or dismiss them. When Add photos… fails after the picks were journaled (for example offline), the notice's Retry starts a sync, because the picks are already queued; it reopens the picker only when nothing was journaled.

### Collaborative gallery deletion

Participants can explicitly delete gallery items from web, desktop or mobile, including a source phone and items not downloaded yet; mobile long-press selects up to 100 (a screen reader gets the same through a Select action on each tile, and a tile announces its kind, filename and date), and Clear selection leaves the mode.

- All clients send the confirmed action directly to the hub and report failures without persistent queues or automatic retries. Partial successes leave the selection and grid; failures stay. A lost response can mean the hub accepted, so refresh before retrying. Conflicts and stale selections keep later content.
- The `galleryDeletion` capability advertises `/v1/gallery/register`, `/delete` and `/removals`, usable with replica credentials under the single-owner model (`/v1/delete-file` stays administrator-only). Native asset IDs stay on the phone; the hub receives an opaque digest, the source credential identity and exact resource paths, hashes and sizes.
- `gallery_assets` and `gallery_members` record verified source groups, registered in bounded batches. A `gallery_assets` row that is not a JSON object, or whose `resources` is not a list of objects, is moved to `gallery_corrupt` at startup (and a row `JSON.parse` rejects is moved when read), so it never stops the app or other assets and never counts as a removed photo; a library photo it described is discovered again and uploaded to the same deterministic path, and a picked photo whose app copy still exists is queued again from the copy under its original name, which is kept in a file beside the app copy so the same deterministic path is used and the hub never gets a second copy (a pick from before that file existed uses the name its set-aside row still carries, else a name taken from the bytes, such as `photo.heic`). Deleting any registered resource removes the whole group, and bulk selection skips companions already removed. Groups are never inferred from names or equal hashes.
- `gallery_deletions` stores durable author and request IDs and tombstone results apart from the proposal cache; reusing a request ID for another target is rejected. All tombstones and pending materializations commit in one SQLite transaction, and replaying an old request cannot delete a restored or edited file.
- Deletion suppresses source uploads in the hub registry and the phone's ledger; losing the ledger or relinking with the same paired identity rebuilds suppression from the `/removals` feed (durable sequence cursor). Restoring history does not reset suppression. Resetting pairing or native identity creates a distinct source that cannot be correlated by name or content.
- There is no review screen, opt-in, native removal of originals, special restore flow or extra recovery retention; ordinary history restore applies under folder retention.

### Mobile gallery

A gallery folder (a linked album or the hub's gallery marker) shows only the photo timeline on the phone and Fold, whichever role the device plays: a phone with a linked album and a phone with an ordinary copy browse the same album. Ordinary folders keep Files and Recent plus a Gallery tab that uses the same component.

- **Order.** The timeline comes from the hub gallery index. The phone lays out the whole timeline from per-month counts and fetches 60-row pages only near the viewport (`hub-gallery.js` keeps each month as a contiguous prefix with its own cursor and a verified-row count). A page is authoritative for the cursor range it covers, so edits, deletions and renames there never stay stale; a month whose count or newest revision changed keeps its rows visible until read again, and rows changing size above the viewport never move what is being viewed. Refresh reads only the newest page every five seconds while foregrounded and on return. The newest 600 rows (path, hash, size, date, kind) and a resumable cursor are cached, so order survives offline; rows without a hub answer fall back to `gallery-date.js` rules, then local modification time. Photos and videos on the phone with no row in its own index (imported while sync was paused, not yet pushed) join the hub index under their own date, once, and cannot be deleted or queried on the hub until they have a revision; names the fixed exclusion list covers (`.git`, `._*`, `@eaDir`, `node_modules`…) never appear, and neither do ones the folder's synchronized `.arcaignore` excludes (read from the phone's working copy; the offline gallery still lists whatever the phone holds), and paging keeps asking the hub only for months it has not read. The cached index is used while linked; once offline is detected, or after two failed refreshes in a row, the phone's own files form the gallery: each is matched by path to the cached index for its capture date and order, and to the phone's own index (`files`) for revision and hash, so Info and the month layout survive offline; only files outside the cached index (its newest 600 rows) fall back to `gallery-date.js` rules, then modification time (a phone with no local files keeps the cached index as placeholders).
- **Viewer gestures.** The viewer opens without its bar. A single tap (told from a double tap after 300 ms) toggles the bar and a filmstrip of neighbouring photos with its position ("N of M"; tapping one moves there); double-tap and pinch zoom and pan as before. Dragging the photo down dismisses it as the Motion section says; swiping up opens Info as the bottom sheet on the phone and does nothing on the Fold, where Info stays a side panel opened by its button; swiping down on the Info sheet's header closes it before the viewer. TalkBack and VoiceOver get Photo details, Show or hide controls and Close photo actions on the photo; Back, Share, Info and Delete and Android Back keep working. The photo does not travel into its grid tile when closing: it shrinks and fades in place.
- **Pixels are local.** The grid, viewer and video read only what the phone holds: its working file, or for album uploads its own Photos original. They render locally first; hub derivatives are a fallback only for verified local originals. A photo not downloaded yet stays a placeholder, and the viewer says it appears once synchronization downloads it. When the platform cannot decode a photo or video that is already on the phone (a large HEIC on Android, for example; no HEVC decoder is bundled), the phone asks the reachable hub for that file's 360 px JPEG (`GET /v1/gallery/preview` with its accepted hash) and keeps it in the same derivative cache, so it is requested once and shows offline afterwards; the viewer does the same for the 2048 px preview (`size=large`) when it opens such a photo, and asks again at every open after a refusal or an unreachable hub. Before asking, and only when the hub could answer (reachable and the file on the phone; for the grid also not paused and not refused), it verifies the local file's SHA-256 against the accepted revision as well as its size; files are hashed one at a time, the viewer's file ahead of the grid's unless the grid already queued that same file, and each verification, including a file that could not be read, is remembered per file revision until Retry or the app returns (a hash that times out is not remembered, and its slot is released after ten minutes even if the read is still running). A local edit, including one with unchanged size, never receives the hub's picture of an older revision; an unreadable local file cannot authorize a hub preview. A hub that refuses, or a preview that cannot be saved, is not asked again this session; a busy hub or one that is not ready yet is asked again; an unreachable hub pauses every request for 30 seconds, and what failed meanwhile is retried by Retry or when the app returns; without the hub the tile stays a placeholder. The timeline itself shows only Needs attention, or Disabled for switched-off uploads, and an Uploading N badge while receipts are pending; the header Sync control and folder rows carry sync state. Pending uploads from this phone sit in a Pending uploads row above the grid (72 dp previews, a remaining count and, for lost photos, the Dismiss N action) and leave it once accepted.
- **Thumbnails.** Tiles show derivatives only, with placeholders until one exists; originals never render in the grid. `ArcaNetwork.thumbnail` renders them natively (360 px thumbnails, 2048 px large previews; `expo-image-manipulator` and `expo-video` are fallbacks on older binaries). Preparation starts with the visible tiles and then covers the newest 5,000 other photos and videos on the phone, newest first and photos before videos, while the folder is open and again when the app returns with failures pending; at most three renders run at once, visible work ahead of background work, and it does not wait for folder listing or restart on sync-status churn or scrolling, a render that never settles frees its slot after 30 seconds, and the saved map drops files that left the folder. A row above the grid says Preparing previews with the count done of the photos on the phone, a second row, "<n> previews could not be made" with Retry, appears as soon as one fails and stays until none fail, and neither row is shown when nothing is missing. The saved map is pruned and written only once the listing is complete, and only when something changed. The derivative cache is one flat directory (`isFlatCacheFile`, `large-` prefix for large previews) in the OS cache, pruned every 200 renders to 512 MiB of thumbnails and 256 MiB of large previews; anything outside the flat layout is deleted at the next render. Paths, sizes and modification times invalidate derivatives, a failed derivative never replaces an original, and a photo whose grid thumbnail cannot be made is attempted once per session, again only after the file changes or the app returns to the foreground (the viewer retries its large preview on each open). Folder removal and destruction clear derivatives.
- **Listing.** Folder walks are coalesced (`coalescedRun`): one walk per folder, re-run only when the replica applies a change to that folder (`folderChanges`) or its file count or size moves. Up to 2,000 listed entries per folder are cached in private SQLite settings and shown before rescanning. Thumbnails reach the grid within a quarter second of completing, and the count in the preparation row refreshes every two seconds.
- **Video.** Tiles, year mosaics and the viewer poster use the first frame of the local file (`thumbnailFiles.poster`; `renderVideoPoster` in `video-playback.js`): native first, else `expo-video`'s `generateThumbnailsAsync` (360 px) saved as JPEG through `expo-image-manipulator` into the gallery cache, releasing the player, frame and image each time. Only `file://` and `content://` sources qualify, never a hub URL or a Photos-derived source; Android paths are decoded first, and iOS retries an empty frame request up to 25 times, 200 ms apart. A video whose frame cannot be read keeps the play-glyph placeholder and is not retried until its size or date changes or the app returns to the foreground. Opening a video plays it at once with native controls in an embedded `expo-video` player; Play remains to retry after an error or on binaries without the module. Only the active video owns a player; swiping and closing release it, backgrounding pauses it, and late async loads never start playback. Info holds the video: opening it pauses, closing resumes only if it was playing or not yet started and nobody moved it. Playback rechecks the working path, falls back to an accessible Photos original, never streams from the hub and shows the native error for unsupported codecs.
- **Viewer.** Full screen on black with swipe paging, pinch and double-tap zoom up to 4× (`PanResponder`/`Animated`, no native dependency). The top bar stays visible: back, capture date, then Share (local copy only), Info and Delete; Share and Delete keep fixed positions and expose disabled state when unavailable. Delete asks for confirmation and sends the shared gallery deletion; the viewer hides the tile and moves to the neighbour. Info (`photo-info.js`) shows name, size, dimensions, megapixels and format, Capture (taken time and offset, camera and lens, aperture, shutter, ISO, focal length), Location with Open in Maps, and In Arca (folder-prefixed path, accepting revision). `exif.js` reads the JPEG APP1 segment and `Image.getSize` supplies dimensions, so it opens offline; `GET /v1/gallery/info` adds the accepting revision and history flag or fills rows without a local copy. An open viewer keeps its sequence while new items arrive.
- **Density and navigation** follow [Gallery on mobile](#gallery-on-mobile) in the design system.

### Music on the phone

A music folder (the hub's marker, not a linked album) opens on its library; the folder menu offers View files and View library to switch, and neither Add photos… nor Link album….

- **Library data.** After every cycle (at most once a minute while a cycle leaves work pending) the phone asks the hub for each selected music folder's library with its saved `version` and keeps the answer in `music_libraries` (scope and folder), so the library also works offline and after restarts; an unchanged answer only updates the indexing flag. An open library reads again when new data or covers arrive, and when tracks finish downloading during a cycle (checked at most once a minute). It lists only tracks the phone holds at the hub's version (its synced row has the same hash), after replaying the phone's own journal of renames and deletions (`journal:<hub>:<folder>` in the settings store, written by Rename and Delete and emptied once a cycle has scanned, pushed and pulled that folder and, for a music folder, the hub's library has been read again): a renamed track moves to its new path with the hub's tags, a deleted track and a deleted or renamed playlist leave the hub's answer, and the car's library file is republished at once. A track the hub lists that is not on the phone reads "Downloading", or "Not on this phone yet" while the hub is unreachable. An album is one music folder's tracks that share a MusicBrainz release id, else the same album directory (a `CD1`, `CD 2`, `Disc 1` or `Disk 2` subfolder counts as its parent), album artist and album title, ignoring case; editions in different directories and the same album in two music folders stay apart, and a multi-disc album stays one when its discs carry the same release id or none; a disc folder directly under the music folder is its own album. Untagged tracks use the file name as title and the album directory's name as album. Album ids are a short hash of that identity. Albums sort by title and an album's tracks by disc, number and path. Artists sort by the first letter of their name (compatibility-decomposed without accents, with Æ, Ð, Đ, Ł, Ø, Œ and Þ read as A, D, D, L, O, O and T), A to Z with every other first character under # at the end, then by name; an artist's art everywhere is the cover of its newest album that has one (latest year first, an album without a year counting as oldest, then title), never cropped to a circle. Failures never fail the file sync and the next cycle retries.
- **Catalog.** A music folder opens on tabs Artists, Albums and Recent, the catalog desktop and the car share, with Artists selected. A search button beside the tabs opens a search field, as in Files: while it has text the library shows Songs, Albums and Artists whose title, artist, album artist, album or name contains it, ignoring case and accents, and a song plays within its album from that song; Back from a result, labelled Search, returns to the results, and clearing or closing the search, Android Back or changing tab returns to the tab. Where the phone can play and the folder has at least two tracks, a Shuffle button under the tabs, hidden while results show, plays this folder's library in shuffled order, and an artist page shows the artist's cover, name and album and track counts with a Shuffle button for that artist in this folder; neither is recorded in Recent. Inside an artist's album the back button carries the artist's name. Artists opens that artist's albums, then the album.
- **Play history.** Recent lists the albums and playlists last played on this phone, newest first, at most 20 and without duplicates, kept in `arca/music-history.json` (format 1, the hub id and the album and playlist ids) and never sent to the hub. On Android the media service records every album or playlist started from the phone or the car, so the car shows the same list; an iPhone records the album it opens a track from. Renaming a playlist moves its entry to the new file; on Android the media service, which keeps the history in memory and owns the file, makes that change, so the car's Recent follows it. Entries that left the library are skipped, and another hub's history is ignored. While no history entry belongs to this folder, Recent shows the 30 albums with the newest additions under Recently added with a caption saying nothing from this folder has played on this phone yet; the car does the same for the combined library. Erasing the device removes the file.
- **Covers.** After a cycle that left no work pending, covers are fetched once per key and size (at most 120 per cycle) into `arca/<hub>/music-covers/<key>-<size>.jpg` in app storage, written through a `.part` file; a key the hub has no cover for (unavailable or 404) is not asked again while the app runs, other failures leave the pass incomplete, and covers no library references any more are removed after a complete pass. The large cover falls back to the small one until it arrives.
- **Car library file.** An Android phone publishes the combined library of every selected music folder as `arca/music-library.json` (format 1, the hub id, cover keys and local `file://` track URIs) whenever it changes, after a cycle, after Stop syncing and before any playback, one write at a time, and tells the native service to reload it; the reload answers only once the service holds the new file, a failed write or reload is retried by the next publish even when the library is unchanged, and Play waits for a publish still running, so a playlist edited a moment earlier plays as edited. Erasing the device removes it and makes the service drop its queue and resume point, also when the service is not running.
- **Screens.** The tabs sit at the top of the library, with a caption below them while the hub reads tags. Artists is an A–Z index: the artists, 120 at a time, in rows under a heading per letter, with album and track counts; an artist opens its albums as a cover grid. Albums is a cover grid of 60 at a time. Recent lists played albums as rows, or the recently added cover grid. An album shows its cover, title, artist, year, track count and length, Play and Shuffle and its numbered tracks 120 at a time. A track whose copy is missing or older than the hub's version stays in its album in disc order, dimmed with Downloading in place of the artist and no length, ignores taps and is left out of every count, search, Play, Shuffle, queue and the car's library; while one is pending the header reads "artist · year · 10 of 12 on this phone" without a length, and "12 tracks · length" once every track is present. Inside an artist or album a back button named after the tab or artist replaces the tabs; Android Back leaves those screens before the folder, and leaves the folder at once when its library is empty.
- **Playlists.** The Playlists tab appears once a playlist exists and opens a playlist like an album. A playlist's rows read "artist · album". The phone edits its own copy of the `.m3u8` files under `Playlists/` (Add to playlist…, New playlist…, Remove from playlist, Rename…, Delete playlist…) through `packages/core/playlist.js` and syncs them as ordinary file changes; it lists its own copy first and the hub's answer for playlists it has not downloaded yet. Add to playlist… refuses a track the list already names ("This track is already in this playlist."), also an edit that has not synced yet. An entry that cannot play (Downloading, Not in this folder, or a line that names no track) keeps its place, dimmed, and keeps Remove from playlist in an editable playlist. A file that is not valid UTF-8 or is over 1 MiB is refused before anything changes, so Rename… never moves it; Rename… also moves a playlist whose edits have not synced yet, with those edits. A playlist the folder's `.arcaignore` or the fixed list excludes is neither listed nor edited ("Excluded files cannot be edited here."), and renaming a track rewrites only the playlists that are not excluded.
- **Android playback.** `ArcaNetwork` ships `MusicService`, a Media3 1.9.0 `MediaLibraryService` (the same Media3 version as `expo-video`) with ExoPlayer, music audio attributes, audio focus and pausing when headphones disconnect. The service loads the published file on a background thread, and browse and play requests wait for it. Tapping a track queues its album from that track; Shuffle plays the whole list in shuffled order from a random track (the `albums` context queues every album of the library in order, an artist id that artist's albums, `in:<folder>:<context>` keeps only that folder's tracks, which is how the phone plays the library or an artist from a folder's screen while the car lists every selected music folder, and only albums enter the play history, recorded without the folder prefix; a long queue checks each cover file once), and turning shuffle on mid-list keeps the current track and shuffles the rest. When the library changes, a queue stops and clears only when its current track left the library and its file is gone, or the library is empty; a track whose file is still on the phone, such as one retagged on another device and not downloaded yet, keeps playing. A resume point that left the library is forgotten. The service owns the media notification, lock-screen and Bluetooth controls and keeps playing in a `mediaPlayback` foreground service; it plays the phone's own files and never streams. The app talks to it through a MediaController (`musicPlay`, `musicCommand`, `musicReload`, `musicState` events). A mini player (cover, title, artist and album, play/pause, next) sits above the tabs in a music folder and opens Now playing: cover, title, artist and album, Go to album when the playing track belongs to the open folder's library (it closes the sheet and opens that album, from View files too), a progress bar that seeks, shuffle, previous, play/pause, next and repeat (off, all, one). Errors name the cause: a missing file, an unsupported format or a generic failure.
- **Android Auto.** The app declares `automotive_app_desc.xml` (`media`) and the car metadata through the module manifest. The service builds the browse tree from the published file without JavaScript, so the car can start Arca cold: tabs Artists (each artist carrying its letter, which the published file holds, as the group title, so the car heads every letter) → albums (a cover grid) → tracks, Albums (a cover grid) → tracks, and Recent, which lists the play history under the Recently played group title or, while it is empty, the recently added albums under Recently added; three levels (a long list adds folder levels, as below), every item with a title and a subtitle and, when the phone holds one, its cover (small in lists, large for the playing track). A track row's subtitle is "artist · length" ("artist · album · length" in a playlist; the length as m:ss or h:mm:ss and left out when unknown), sent as a display title and subtitle because Media3 otherwise shows the artist and album; Now Playing keeps the artist and album. The queue is named after the album, playlist or artist it was set from (the player's playlist title, which Media3 hands Android Auto as the queue title), and has no name for the whole library or a hand-built queue. Search and voice requests are not offered. Android Auto asks for whole lists and Media3 cuts each answer at 256 KiB (roughly 300 items, fewer with long titles), so Artists, Albums and an artist's albums with more than 120 entries open on folders instead: the first letter of the artist's name or the album's title (the same fold the library file's letter uses: accents and width folded, Æ Ð Đ Ł Ø Œ Þ to their letters, digits and symbols under # last), each folder titled with its letters and counting its items; a letter still over 120 splits on its next letter, down to three letters, and a group whose names share all their first letters is cut into numbered ranges ("1–120", "121–240") so no level repeats itself and every artist and album stays reachable. Shorter lists stay flat. The folders are not playable and playing still goes through an album, artist or playlist. Albums keep their cover grid under their folder, while a list of folders reads as rows. Folder contents are read when opened; the car's lists refresh on reload only at the tabs. Covers reach the car through the exported read-only `CoverProvider` (`<package>.arcamusic`), which serves only `arca/<hub>/music-covers/<key>-<small|large>.jpg`. Nothing plays until the driver picks a track. The last track, the position where playback last paused or changed track, and whether shuffle was on are kept, so a play request with nothing queued, from the car or the system media controls, resumes that album, artist or library queue there. No media button receiver is declared, so a headset's Play resumes only while the service runs.
- **iPhone.** The library and covers work the same; a track opens its file detail (Open, Share) and Play and Shuffle are hidden until the iPhone player ships.

### Incoming sharing

Arca registers as a system Share target (Android `SEND`/`SEND_MULTIPLE`, iOS Share Extension). Receiving is transient: up to 20 incoming files are copied under safe internal IDs into a private cache while the destination sheet (Save file or Save files) is open. The user picks a folder already selected on this device, or one of its subfolders, or types a relative subfolder such as `workouts/2026`; selection is rechecked at Save, and nothing uploads before Save. Each Save records its destination (folder ID and subfolder) in the phone's own `settings` row `shareDestinations:<hub>` with a use count and last-used time, capped at twenty entries and pruned of folders the sheet no longer offers as a Selected folder here (unselected, or now a gallery); the sheet offers the three most used (ties by most recent) as Recent destinations above Selected folders, one tap opening that folder at that subfolder with Save here ready, and the ledger never leaves the phone. Saving writes locally, so it works offline or paused and uploads later, with existing differing content preserved by the normal conflict behavior. X, Cancel and Android Back discard the whole batch at once; a new share replaces an unsaved batch; cancellation during resolution or copying invalidates late results; startup deletes abandoned copies and never restores a sheet. Links, text, `text/plain` streams, unsafe paths, incomplete files and (on iOS) duplicate resolved temporary names are rejected with a recoverable message. On Android Arca copies each shared `content://` file itself (`ArcaNetwork.receiveShared`) straight to a generated name in its own inbox, refusing `file://` and other schemes and its own providers (the authority is read without any user id prefix); the sender's display name is only read as a label and never becomes a path, so the library's cache copy named after the sender is never used. An incompatible single-component sender name stays staged with an editable File name field validated at Save; sender-supplied paths are rejected. Without a hub connection or selected folders, the sheet explains the prerequisite. Incoming sharing never selects or downloads another share. The iOS extension is experimental in Expo.

## 8. Operations

Commands run from the repository root unless stated otherwise. Each environment owns its commands: the root keeps the daemon, tests and site; `apps/desktop` has `start`, `start:clean`, `ui`, `build`, `release` and `verify:bundle`; `apps/mobile` has its build scripts.

### Desktop development

Requires Node.js 24+, Rust and the platform's Tauri prerequisites.

```sh
npm ci
npm start --prefix apps/desktop
npm test
npm run build --prefix apps/desktop
npm run verify:bundle --prefix apps/desktop
```

- `npm start --prefix apps/desktop` runs `scripts/desktop-dev.js`: it checks that Vite's loopback port 1425 is free (failing without touching the daemon otherwise), identifies the local daemon by state lock and process command, stops it, stages the checkout's runtime, starts it and waits for the IPC-ready notification plus authenticated identity and lock checks before opening Tauri. A loaded macOS LaunchAgent whose executable, CLI and state arguments match this checkout is unloaded before staging and bootstrapped afterward (restored if staging fails); other services are untouched. It refuses unrelated PIDs, fails visibly on timeouts and never initializes state: a missing config opens first-run onboarding. `ARCA_HOME` selects state for the launcher and the native bridge; the default is the real `~/.arca`. The CLI interrupts active sync on termination.
- `start:clean` clears only the repository's Vite caches, then starts normally. Vite serves the UI on port 1425: CSS updates live, HTML and JS reload, Rust changes rebuild Tauri. Daemon changes need the launcher or a service restart.
- `stage-runtime.js` and the development launcher first run `scripts/prune-cargo.js`: a Cargo `target` over `ARCA_CARGO_BUDGET_GB` (10 GB by default) loses its incremental caches, then is removed if still over; pruning is best effort and never blocks a start or build.
- The build downloads the official Node named in `.node-version`, verifies its checksum and bundles it with FFmpeg (`ffmpeg-static`, license kept) and locked production dependencies; the first build needs network and caches under `.cache/runtime`. Staging and bundle verification execute the bundled FFmpeg and fail clearly if install scripts left it unavailable. macOS output is `apps/desktop/src-tauri/target/release/bundle/macos/Arca.app`, ad-hoc signed; close a compiled app from its tray menu to avoid confusing it with the dev window.

### Validation and versioning

- `.node-version` is the one Node version. CI (`node-version-file`), the bundled desktop runtime (`stage-runtime.js`) and local validation read it; the Docker base image and the EAS profiles keep literals that a test holds equal to it.
- `scripts/release-manifests.js` lists every version location (manifests, lockfiles, native modules, reported versions and the README, SPEC and `design/` banners). `node scripts/bump-version.js [x.y.z]` rewrites all of them at once and `node scripts/check-release.js` checks the same list, whatever the line endings, plus the changelog entry and that the Android versionCode, iOS buildNumber and native module versionCode are equal. Mobile build numbers are explicit and increase only when a native release is prepared.
- `npx -y node@<.node-version> scripts/validate-local.js` (it refuses any other Node and prints the command) copies the working tree into a clean temporary checkout, runs root-only `npm ci`, the version check, the CI suite, off Linux the mobile source suite, and the mobile build-tooling tests. It keeps failures for inspection. Root-only installs matter: the development workspace can hide an undeclared root dependency through `apps/mobile/node_modules`.
- CI runs the whole suite on Ubuntu and everything except `tests/mobile-*.test.js` on macOS and Windows. Tests build paths with `path.join`/`path.sep` and file URLs with `pathToFileURL`/`fileURLToPath`, accept CRLF checkouts and never assume one platform's temp directory. Windows refuses to truncate or remove files another process holds, so fixtures reuse or restore content in place and cleanup retries with backoff. DOM tests wait for `body[aria-busy="false"]` and drain pending native requests and their render callbacks before closing JSDOM; their delayed-response regressions stay. Tests that run `git` strip inherited `GIT_*` variables, because a pre-push hook in a linked worktree would otherwise act on the real repository.
- `.githooks/pre-push` (enable with `git config core.hooksPath .githooks`) repeats the version check and the CI test command with the CI reporter, except that it skips the suite when `validate-local.js` already passed on these exact files: that script writes a stamp (a hash of every tracked and untracked non-ignored file, in the git directory, never in the tree) only if the files did not change while it ran, and the hook compares it before running anything; the Node version is not hashed because `validate-local.js` refuses any Node except the one pinned in `.node-version`, and that file is hashed, so a pin change invalidates the stamp. Both the hook and `validate-local.js` run `node --test` with `--test-concurrency` set by `scripts/test-concurrency.js` (half the cores, at least one; `ARCA_TEST_CONCURRENCY` overrides) so a full local run does not saturate the machine; CI keeps Node's default. Neither the hook nor `validate-local.js` compiles Rust; no local script runs the desktop unit tests.
- `npm test --prefix apps/mobile` checks the mobile build script wiring.

### Isolated qualification

- `node scripts/verify-scale.js` creates an isolated hub and replica and checks 1,000 full files (`ARCA_TEST_FILES` accepts 1–10,000).
- `node scripts/verify-resilience.js` runs temporary hub, replica and backup processes: SHA-256 manifests, concurrent edits, rename and deletion, SIGKILL during a partial upload, restarts, restoring a synchronized backup into a fresh hub through the replica's `/v1/backup`, and six minutes of scheduler observation without writes.
- `node scripts/verify-hub-load.js . 100000` seeds a temporary hub (one third tombstones), runs three concurrent initial snapshots alongside a real 1 MiB upload, proposal and verified download, pages through a snapshot, checks that totals exclude tombstones, pause and resume, probes discovery with a two-second deadline and enforces 15 seconds per snapshot. On a Docker host with a built image:

  ```sh
  docker run --rm --network none --cpus=1 --memory=1g \
    --mount "type=bind,source=$(pwd)/scripts/verify-hub-load.js,target=/tmp/verify-hub-load.mjs,readonly" \
    --entrypoint node IMAGE /tmp/verify-hub-load.mjs /app 100000
  ```

All three use temporary state only and log counts and timings, never credentials or content. They are bounded checks, not sustained multi-device load, power loss, battery or multi-day soak evidence.

### Release pipelines

Three workflows own one artifact each, and a fourth keeps the repository tidy.

- **`publish.yml`** (display name `publish`) checks version agreement, runs the JavaScript test matrix and, in parallel, `rust-tests` (`cargo test --locked` for `apps/desktop/src-tauri` on macOS, with an empty `runtime/` because tauri-build requires the resource directory), both on pull requests too; publication waits for both. It then builds macOS Apple Silicon DMG, Windows x64 NSIS and Linux x64 AppImage and deb on three runners. A push of a new version to `main` publishes; manual runs can build artifacts only. An existing remote version tag skips building and publishing; a failed remote lookup stops the run. Package checks mount the DMG, extract both Linux packages or silently install NSIS, then initialize isolated state and verify the packaged daemon's authenticated API and the absence of desktop web access; they do not certify native UI or OS integration. Verified installers upload directly to a GitHub draft release pinned to the checkout SHA; the final job downloads the four installers, checks they are nonempty, writes `SHA256SUMS` and publishes the prerelease; then the `updater` job writes `latest.json` and moves `desktop-latest`. A failed publication keeps the draft for a retry from the same commit; a draft from another commit or an unrelated tag stops for inspection. No installers or images are uploaded to Actions and Docker build records are disabled.
- **On macOS** the release builder compiles once with `build --no-bundle` and bundles with at most one retry; Windows and Linux use one combined invocation, and CI mode avoids interactive Finder customization. The embedded Node is signed before the app with its JIT entitlement and `com.apple.security.cs.disable-library-validation`, which only that executable carries, so it can load the bundled `sharp` addon. Launch at login is macOS only. Two Unix-socket tests are skipped on Windows.
- **`publish-docker.yml`** builds and smoke-tests amd64 and emulated arm64 (shutdown, restart, persistent identity and files). After a successful `publish` push run of this repository on `main` (never a fork's pull request: the gate also checks branch, repository and event, as `publish-site.yml` does) it checks out that run's commit (`workflow_run.head_sha`), so rapid pushes never publish a newer image or record its tag before that version's release exists, and pushes `satoshiltd/arca:X.Y.Z` and `latest` to Docker Hub and records a `docker-vX.Y.Z` tag (`scripts/record-docker-tag.sh`: four attempts, an existing tag counts as done, and a final failure names the exact `gh api` command to run by hand) in a `record` job that runs after a successful publish, so a failed tag re-runs alone and never rebuilds; when the version is already on Docker Hub without its tag, the gate skips the build and the same job records it, and any Docker Hub answer other than 200 or 404 stops the run instead of publishing. The cause of the 403 seen on the refs API at v0.6.84 was not found. Pull requests touching `deploy/`, `packages/` or the image verifier build and test without pushing. The image reaches Docker Hub minutes after the GitHub release; the two are never atomic.
- **`publish-site.yml`** deploys the website (below).
- **`prune-actions.yml`** runs every Monday at 03:17 UTC and by manual dispatch (`dry_run` only lists). `scripts/prune-actions.js --apply` deletes completed runs beyond the newest 10 per workflow that are older than seven days, and artifacts older than seven days; without `--apply` it only lists. Running work, releases and caches are never touched (GitHub evicts caches itself).
- Android builds are manual EAS commands and never part of a pipeline.

#### Release setup and publication

Unsigned artifact runs need no custom secrets. macOS installers are ad-hoc signed and Windows installers unsigned by default; Windows signing is not implemented. For Developer ID signing and notarization, add these repository secrets (Settings → Secrets and variables → Actions), then run **publish** manually with **sign_macos** checked and **publish** unchecked to verify:

| Secret                       | Value                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------ |
| `APPLE_CERTIFICATE`          | Base64 of the Developer ID Application `.p12` certificate with its private key |
| `APPLE_CERTIFICATE_PASSWORD` | Password used to export that `.p12`                                            |
| `APPLE_SIGNING_IDENTITY`     | Full identity, e.g. `Developer ID Application: Your Name (TEAMID)`             |
| `APPLE_ID`                   | Apple account used for notarization                                            |
| `APPLE_PASSWORD`             | An app-specific password                                                       |
| `APPLE_TEAM_ID`              | The Apple Developer team ID                                                    |

Export the certificate with its key from Keychain Access and encode it with `base64 -i certificate.p12 | pbcopy`. GitHub never reveals saved secrets, so reuse the original source if Alf already holds them. Never put certificates, passwords or tokens in source control or chat. See [Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/).

Docker Hub publication uses `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` (read/write, not delete, on `satoshiltd/arca`); GHCR is not used. The updater needs `TAURI_SIGNING_PRIVATE_KEY`.

To publish: bump the version and changelog, validate, commit and push to `main`. The workflows build, verify and publish; `latest` follows the newest release and is not a stable-release guarantee. If the final GitHub job fails after the image push, the versioned image and `latest` may already exist: retry the failed jobs from the same commit after inspecting the draft. Publishing restarts no installed daemon. `npm run release --prefix apps/desktop` builds platform installers locally; `npm run build --prefix apps/desktop` builds the local macOS app.

### Website publication

`site/` is one responsive English page: static HTML and CSS, local Instrument Sans and Fragment Mono, the Arca mark and local monochrome platform icons, with no navigation menu, framework, telemetry or runtime API. ### Shared geometry

- **Touch.** Mobile buttons and single-line fields use `--touch-control-height` / `geometry.touchControlHeight` (48 dp); compact icon controls keep at least 44-dp targets; normal icon-only buttons are 48 dp squares with 20 dp icons, and `Button size="small"` matches desktop's 32px with 16px icons. Fields reserve their height before text entry, center text without Android font padding and give icon-wrapped fields the same outer height; accessibility font scaling may grow them, but text or focus never changes their height. Buttons keep a minimum rather than a fixed height.
- **Lists.** `--list-item-gap: 12px` and `geometry.listItemGap: 12` separate sibling list cards (folder lists, selectors, onboarding); contiguous rows inside one grouped surface keep zero gap and a divider. Shared row padding is 10 vertical and 12 horizontal.
- **Details.** Two-column folder and file details share a 320px/dp side column (`--detail-side-width`, `geometry.detailSideWidth`); the main column takes the rest; narrow layouts stack.
- **Tags and pills.** Role tags use Fragment Mono 10/14, a 6px radius, 1px border, 2×5px padding, a 20px outer height and uppercase text, laid out as an inline grid that never shrinks. Status pills use Instrument Sans semibold 12/16, fully rounded, 4px vertical padding. The Hub tag and hub tiles use the accent background and on-accent foreground; the current-machine tag uses tint and deep.
- **Explorer.** The breadcrumb bar is a fixed 37px row (24px control, 12px padding, divider) inside the bordered file panel, using `--text-caption` and 12px icons, horizontally scrollable, even at the root, so navigation never shifts the list. Files and Recent rows share typography: title `--text-control` weight 600, metadata `--text-body`, 2px between lines. The Files/Recent toolbar sits 6px above its content with no extra margin.
- **Icons.** Lucide 0.460.0 geometry everywhere; mobile renders the same node data through react-native-svg with aliases in `icons.js`, checked against the desktop vendor bundle. `apps/desktop/src/file-icons.js` maps extensions to Lucide icons for both clients (text, PDF, ebooks, installers, images, video, audio, archives, spreadsheets, presentations, code); unknown files use File and directories Folder. Machine disconnection uses Unplug; folder unlink keeps its own icon. History uses trash-2 (muted, struck-through name) for deletions, triangle-alert (amber) for conflicts and git-commit-horizontal for revisions. A conflict is triangle-alert on every surface, desktop and phone: pills, stats, History rows, the No conflicts empty state, the Resolve conflict dialog and the conflict notice.
- **Placeholders.** Media placeholders are one element on every gallery surface: the `placeholder` token (light `#e4eae5`, dark `#1f2a24`, identical in `tokens.css` and `palette.js`) with a centered 20px image glyph, or a play glyph for video, in `line` colour. Mobile shows the glyph only on tiles of 48 dp or more (`MediaPlaceholder`). Unfetched cells and loading thumbnails look the same.

`apps/mobile/src/design-tokens.js` mirrors them. Only opacity and transform animate; layout dimensions never do; no animation library is used; reduced motion collapses durations and movement to zero and makes activity indicators static. No decorative animation on polls or row updates, except the single arrival settle below.

- **Desktop and web.** A route change fades and lifts the content in over 200 ms (opacity .65 → 1, 6px); same-route refreshes never replay it. On a new route the first six rows also rise 8px in turn, 20 ms apart (`--motion-stagger`); refreshes never replay that. A row that appears on the visible route after its first render (a file arriving through sync; at most six at once, never rows already there) rises once and holds an accent tint that fades over `--motion-settle`. Opening a photo animates the viewer image from its thumbnail's rectangle over `--motion-shared` (transform only, falling back to the fade when the thumbnail is off screen), and a folder card's tile travels into the detail header tile the same way; closing the viewer stays immediate. Dialogs, menus and notices animate their entrance only and dismiss immediately; closed dialogs never linger in the top layer. Updating an existing notice keeps expanded details and does not replay its entrance. The photo viewer fades only on opening, without scale; photo navigation and thumbnail-to-preview upgrades are immediate. Photo Info slides and fades in over 200 ms and out over 140 ms, disabling focus at once when closing; repeated toggles cancel the previous animation. Command-I or Control-I toggles Info only in the viewer, ignoring editable controls and key repeats.
- **Mobile and Fold.** Bottom tabs cross with a plain fade. Opening a folder or file pushes the screen in from the right by 30 dp with a fade and back pushes from the left (`ScreenEnter` inside `KeyboardScrollView`; `App.jsx` derives the direction from screen depth). `Sheet` drives its own `Modal` with `animationType="none"`: on phones the panel slides up by its measured height while the backdrop fades; on the Fold and for centered dialogs it fades and scales from 0.9. Exits play before unmounting (`useRetained`), and Android Back and Close run the same exit; a closing modal takes no taps and a reopened sheet re-enters. The photo viewer opens with a fade and without its bar; dragging the photo down moves it and shrinks it toward 60% with the finger while the backdrop fades over half the screen height, releasing past a third of the height (or with a fast flick) closes it and releasing earlier (or a second finger or an interrupted gesture) eases it back over `--motion-enter`, and on the phone releasing an upward drag past an eighth of the height opens Info; a single tap fades the bar and a filmstrip in over `--motion-fast`. All of it moves only opacity and transform, and reduced motion makes it instant. On Folders, the first six rows of "Selected on this device" rise 8 dp in turn, 20 ms apart, the first time the list shows; a folder that appears afterwards while the list is open (at most six at once) rises once and its row holds the accent tint (starting at 70% opacity), which fades over `--motion-settle` (`Rise`, `list-motion.js`); a whole new list is never an arrival. A pressed folder row, button or action row scales to `--motion-touch-press-scale` (.98) instantly, without easing. Opening a photo from a grid tile grows the viewer from that tile's measured rectangle over `--motion-shared` (transform and opacity, `viewer-origin.js`), and Back or the Close button shrink it back to the tile while the photo shown is still the one that was tapped; a tile that cannot be measured or is off screen, another photo reached by paging, search and the drag-down close keep the plain fade or the drag. On the Fold a folder row's tile travels into the folder header's tile over `--motion-shared` (`flight.js`, `useFlight`); the phone's header has no tile. The selected tab's tint (phone bar and Fold rail) slides to the new tab over `--motion-fast` while the screens cross-fade. A syncing folder row with a known byte total draws a progress ring around its tile from two clipped half arcs rotated by the fraction (the per-file transfer of the current download or upload, not folder-wide); without a total the busy dots stay. Pulling Folders down starts a sync with the platform refresh control in the accent colour. Buttons and action rows scale like folder rows while pressed. Not built: the mini player's cover growing into Now playing, the edge swipe back and the arch mark that follows a pull. Each row plays its motion only when it first renders, so leaving a folder and coming back never replays it.

### Navigation and hierarchy

Web and desktop use hash routes: `#/folders`, `#/folders/SHARE_ID`, `#/machines`, `#/history` and `#/settings`, with History's `volume`, `path` and `filter` in the fragment. Direct links, reload and Back/Forward restore the view; login keeps the requested route; unknown routes and missing shares return to Folders. The current page has `aria-current`. Folders, Devices (always "Devices", on hubs and replicas), History and Settings are shared; data and actions vary with real permissions, never geometry or vocabulary.

- **Search.** Command-K (Control-K on Windows, Linux and the web) and the Search field at the top of the sidebar open one palette dialog from any page (`#palette`, `--dialog-wide-width`): a field, scope chips All, Files, Photos and Music, and results grouped Folders, Files, Photos (a thumbnail row), Music (title, artist and album) and, for a short action name, Actions, each capped at six rows with its count. Up and Down move across groups, Enter opens the folder, the file's detail or, for a photo or a track, its file detail (the viewer and the album are not opened from here) and plays nothing, an action runs and closes, and Esc, a click outside or the shortcut again closes and returns focus. An empty field lists the last five opened searches and the actions (Sync now, Pause or Resume sync, Choose folders… or Create shared folder, Open Settings); a query without results shows the empty state; the footer says it searches this device. `GET /v1/search?q=&scope=all|files|photos|music&limit=` ranks names (exact name with or without its extension, prefix, contains, then every word in the path, track title, artist or album) over the current files of the selected folders (every folder on a hub) from the local index, skipping deleted and ignored files; it is admin-only and needs no new index.
- **Folders:** a Just arrived strip of the three newest changes across the selected folders (file, originating device, relative time; deletions are not arrivals; each opens its file detail; hidden when empty), then selected working copies, then available shares; Choose folders is the replica's primary action (Connect to hub… while disconnected) and the hub owns share creation. The header holds that button and an empty Folders only explains, pointing on a replica to the available rows below when there are any.
- **Folder detail:** see [Folders and details](#folders-and-details).
- **Devices:** Hub connection, then one Devices list, then backup information. Pairing and removal belong to the hub. Discovery is not linking, network presence is not verified sync, and reports carry their real freshness.
- **History:** day groups headed Today, Yesterday or a short date (the year only when it is not the current one), each row ending in its HH:mm clock time in the same way on desktop and phone (Recent keeps relative times), and bounded pagination that appends under one Show more button (a file's history says Show more versions, the phone too); placeholder rows carry no label; a shared-folder dropdown defaults to All, and Conflicts and Deleted are mutually exclusive toggles (clicking the active one clears it). Folder and type filters combine and survive each other's changes. The default excludes deletions and conflict-copy versions. Rows open file history from the whole row with an accessible file name, Enter/Space activation, a hover background, an inset focus outline and the bare muted chevron; conflict rows open review without a separate button. Filter counts are numeric badges. Restore never predicts a version number.
- **Settings:** replica connection first, then identity, service, access, appearance and maintenance, all sections always expanded (no accordions). Service holds the version, Copy diagnostics, runtime and state paths; Appearance only display preferences. Advanced explanations sit beside their control or in a dialog.

The shared segmented control wraps its segments onto another row when they do not fit; its fill variant (`segmented-fill`) shares the row in equal flexible segments with centred labels that never break and `--space-1` side padding, narrowing them toward their labels when tight and starting another row only when the whole labels cannot share one, so a narrow page never scrolls sideways. The shared dropdown has a 32px control, 13px Instrument Sans, control-radius border, semantic colours and a Lucide chevron; its menu uses the menu shadow, compact rows and a check beside the selection. Long labels truncate and long menus scroll. Arrow keys, Home/End and typing navigate, Enter/Space select, Escape, Tab and outside clicks dismiss, and focus returns to the trigger. Segmented controls (Files/Recent, history filters, theme, network mode, retention, text size) share one component with named groups and `aria-pressed`; toggles share one component; directory pickers use a named 32px icon button in the field-with-icon wrapper; every Select action (Folders, Recovery) is the same secondary small button with the download icon. Shared icon actions use `data-tooltip` plus `aria-label`: a 200 ms delayed tooltip mounted outside the control and clamped to the viewport, dismissed by Escape, click, blur, scroll, resize or removal. Ghost icon buttons are borderless 28px controls with token hover fill.

### Managed role and access surface

The desktop daemon publishes no web panel; server installations provide the browser UI. Role decides device authority; web or native decides browser sessions and OS capabilities. Never infer remote administration from pairing.

| View          | Hub                                                                            | Replica                                                                                               |
| ------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| Folders       | Create shared folders, inspect catalog and hub working copies                  | Select folders and choose independent destinations                                                    |
| Folder detail | Rename, edit policy, retention, disable the hub working copy, delete the share | Open, move or unlink the local copy; read-only retention; shared history while connected              |
| Devices      | Issue pairing codes, remove devices, grant web approval, see reported backups | Hub connection with Disconnect/Reconnect, local device status; discover hubs only while disconnected |
| History       | Shared history and restore                                                     | Shared history for selected folders and restore while connected; disconnected views ask to reconnect  |
| Settings      | Synchronization, network, discovery, retention, Images, Danger zone            | Hub connection, local sync, optional full backup, advanced replacement-hub recovery, Danger zone      |

Web alone shows Sign out and Sign out all browsers; desktop alone shows launch at login and native notifications. Disconnected replicas keep their folders and paths visible without remote-only actions, and folder details explain that history and sync need reconnection. The same Disconnect action appears on both sides; a desktop request needs a reachable hub and stays retryable, while a hub-side removal reaches the replica at its next contact. Disconnected device rows use a static Unplug icon and warning tone, never the busy animation.

### State and progress

- **Vocabulary:** Up to date, Syncing, Scanning, Paused, Pending, Conflict, Needs attention and Offline. Paused is a warning tone on every device, tray included, and Disconnected uses the Unplug icon. Offline is the warning state of a device whose hub is unavailable: it replaces Up to date and Syncing in the current device's Devices pill and in the tray heading (a paused or failing replica keeps Paused or Needs attention), and saved rows of other devices read last known, with an Offline pill only while the hub really is unavailable. Recent and a file's history with nothing saved read "No saved versions" and "Offline. Connect to the hub to load its history." instead of claiming there is no history. Unknown values stay unknown, never zero or success: "No completed sync yet", "Not counted yet". A selected folder is up to date only after verification.
- **Progress** counts files and their bytes per phase: "402 / 1,269 files sent · 4.3 GB / 14.0 GB · path" when uploading, "files checked" when receiving or verifying. Directories and deletions never count; empty files advance the counter. A full receipt takes its totals from the hub catalog's file count and size, read again when the same cycle proposed changes, and never falls below the count done; an incremental receipt has no total. Without a folder total, show the current file's bytes only when known and nonzero. Never simulate a percentage; paused folders show no active progress; copy names the phase when the count restarts.
- **Loading.** Views keep current content during refresh and never replace a populated view with a loading message. First loads use static scaffolds (`scaffoldLine`, `scaffoldRow`; card, history and compact geometry, optional dashed boundary) with one representative row, never a fabricated count; known data paints immediately. There is no top loading line and no minimum loading delay.
- **Empty states.** An empty state is an icon, a heading and one line. It carries its own button only on a view whose header has none: History while disconnected (Connect to hub…), Devices on a backup device without a hub (Connect to a hub), the Service stopped page (Start service) and a failed load (Retry). History says why it is empty: with the Conflicts or Deleted filter it names the filter and how to clear it (also from saved data while the hub is away; "History unavailable offline" is only for when nothing is saved), a folder filter says so, and the phone's offline, filtered and empty cases each have their own line and icon. Desktop and phone share the wording: "No history yet" with "Changes to your files appear here.", "No changes in this folder" with "Set Shared folder to All to see every change.", "No photos yet" with "Photos added to this folder appear here.", and Recent's "History appears after the first sync.". A view whose header owns the action, as Folders does, never repeats it inside the empty state; the disconnected replica's Hub connection card is a settings card with its own Reconnect….
- **Activity.** During API, view, action and sync activity the shared nine-dot Busy grid replaces only the interior arch of the sidebar Arca mark; the green tile and geometry stay. It appears after 300 ms, stays at least 500 ms once shown, and status or approval polling does not count as activity. While a folder syncs or scans, its leading folder or gallery tile shows the nine dots instead of a status chip.
- **Quiet rows.** Folder rows omit Up to date: synced rows keep their icon and chevron; pending, incomplete, paused, disabled and error states stay explicit. Desktop folder rows show no relative completion time.
- **Sidebar status card.** A bordered card with the state on the left and two icon buttons on the right: Pause/Resume and Sync now, with tooltips. Sync now is omitted while syncing or scanning and disabled while paused. "Last sync …" appears on a second line only when not Up to date. A separated backup row shows the hub's backup report count (or pending/none) or the replica's full-backup state, linking to Devices on the hub and Settings on replicas, without claiming a backup is current. Offline replaces Syncing while the hub is unreachable, and one global Offline indicator replaces per-card badges. Headers and Settings do not duplicate these controls, and folder details never offer a per-folder pause.

### Feedback and dialogs

One pure contract, `apps/desktop/src/notice-contract.js`, owns notice kinds, content, queue and metrics; web and Tauri import it, mobile imports the same module, and the daemon supplies its system-notice payload. Metro watches its directory (restarting Metro is the maintainer's), and the staged runtime and `.easignore` include it.

- **Variants.** Info: the primary green with its on-green text and link, dismissed after four seconds, optional link. Warning: neutral notice surface, attention icon, persistent, action plus Dismiss. Error: neutral surface, alert icon, persistent, optional Details/Copy footer. The warning and error dark surface is `#1f2521`; notice colours are dedicated tokens.
- **Geometry.** 360 logical units wide within the viewport, 16 inset and padding, 14 radius, 12 stack and content gap, 20 icon, 15/21 title and 14/21 body. Desktop sits bottom-right, mobile bottom-center above the safe area with 16 side margins, above open sheets. At most three stack upward. Entry is an eight-unit upward fade (desktop `--motion-enter` with the shared ease, mobile 180 ms from the contract with React Native's default ease-in-out), respecting reduced motion; mobile allows swipe-down dismissal. Mobile link and footer targets stay 44 dp; desktop Details is 32px.
- **Incidents.** Entries are keyed by condition and folder, never per file. Connection and authentication failures across folders, backup and actions share one hub notice. Permission failures never ask to pair; 401 asks to sign in without claiming revocation. Replicas ignore unselected folders. The hub catalog owns conflict counts and a conflict version marker, so a new or edited conflict notifies again while resolving one alone creates no incident. Polling keeps the DOM, expanded details and dismissal for an unchanged incident; recovery resets suppression.
- **Details** start closed with chevron, Details and Copy on a paper-tone footer; opening reveals a scrollable monospace trace. Copy uses the displayed redacted text (bearer credentials, credential fields and URL userinfo removed) and reports success only after the clipboard write. Never add request bodies, secrets or codes. Technical text belongs in Details; native cancellation is not an error. Field validation stays inline; operational errors use notices.
- **Dialog anatomy.** Every web and desktop dialog shares one anatomy: `--dialog-width`, `--dialog-padding`, a `--dialog-tile` icon tile beside a `--dialog-title`/`--dialog-title-line` title (16/22px) and a `--text-control`/`--dialog-body-line` consequence (13/20px, the size of the buttons), then fields (12px labels, 11px hints, 12px secondary paragraphs and callouts), then Cancel and an explicit verb. The tile uses the brand tint, the warning tint for conflicts and the error tint only for destructive actions, whose submit is the filled red primary (`danger`). Dialogs without fields are confirmations: actions align with the text column, one inline option (`.confirmation-option`, the shared toggle with a one-line label) may appear, and Cancel holds initial focus. Form dialogs never dismiss on backdrop clicks and contain their scrolling. Mobile uses in-app `ConfirmDialog` with the same anatomy.
- **Submitting** shows a busy indicator on the existing action with `aria-busy`, a stable label and no duplicate submission. Cancel and Escape stay available: closing detaches the submission without cancelling accepted work, its later error appears as a notice, and a submission detached before starting is never sent. On failure the dialog stays open with the error; on success it closes or advances.
- **OS notifications** keep OS chrome and the app icon with the in-app title and body. They fire only while the app is in the background, once per condition until recovery or a new conflict version, grouped by folder; hub-unreachable conditions wait at least a minute; there are no completed-sync or reconnection notifications. Mobile responses carry a bounded route and action payload; desktop body clicks open the relevant screen and Retry now also syncs. Delivery failure never stops sync.
- **Quiet successes.** Changes already visible in controls (names, renames, toggles, launch at login) do not toast; a mobile name waiting for the hub still explains the delay. Every Copy action shows a check and "Copied" for two seconds, never a toast. Restores and conflict choices offer Show. Exporting opens the system share UI without claiming the receiver saved it. Clipboard fallback over HTTP creates its temporary field inside the open dialog, restores focus and removes it; desktop uses its native clipboard.

### Copy rules

- The sidebar shows the lowercase `arca` wordmark and one device identity row (name and role); prose uses `Arca`. Never repeat the name beneath the wordmark or add "Managing".
- "Shared folder" is a hub-published folder and "local copy" its working directory; "Folders" is the navigation section. Use Rename, Create shared folder and Delete shared folder; API names may say share or volume.
- In ordinary copy say Hub or the hub, not its configured name; device identity stays where users tell devices apart (roster, copies, version authors). Incoming sharing says Save file / Save files.
- Short sentences and concrete verbs: Start syncing, Restore as new version, Stop syncing. One piece of information per place; paths, IDs and protocol detail below the main label. Keep operational constraints where they affect a decision, not as permanent paragraphs. Top-level views have no subtitles repeating counts or identity; folder detail keeps its local count and size.
- Destructive and preserving consequences stay in confirmations (unlink, restore, cleanup, Remove device, destroy). "Remove {name}?" on the hub confirms loss of access and deletion of the device's registration and reports; files and history remain and reconnecting needs a new code.

### Folders and details

- **Folder rows** show name, count and size (the local path lives in the folder detail; available rows say they are on the hub in their section heading). The tile is the folder's type icon: Images for a gallery folder, Music for a music library, Folder for the rest; a folder card never shows file content. While syncing, a ring around the tile fills with files checked or sent (the nine-dot sits in the tile; an indeterminate cycle draws no ring) and a conflict draws the ring in the warning colour. Left and Right walk the folder's files, Space or Esc close and return focus to the row, Enter or Open runs Open file. File detail shows the same preview above its stats for an image, video or text file. Previews come from the local copy; a hub reads the stored object of the current version.
- **Files/Recent.** Files lists the accepted index (never arbitrary host paths) with breadcrumbs, pages of 100 rows that append under one Show more files button (up to 500 rows, then a hint to search; scroll and the applied search stay, every render re-reads the loaded pages in sequence from the first, taking each cursor from the previous answer, so a folder that changes never skips or repeats rows) and search from the magnifier over the current breadcrumb's descendants; closing search clears it. Rows with media show a 44px thumbnail loaded near visible rows with bounded concurrency; history rows request the exact retained version and never substitute the current photo. Empty explorers read "This folder is empty" or "No matching files" with a muted folder icon inside the panel. Returning from a file keeps the directory.
- **Copies** lists devices from the hub's reports plus the current local selection, with tags only where they say something (Hub, Album source, This device); reports older than two minutes or kept while the hub is unreachable are last known, and the list says "Hub unavailable. Showing last known copies." whenever it comes from saved data. Synchronization state belongs in Devices.

After validating a destination, show "Counting local files…" then one caption: count, size and available space for existing folders, "New folder · available space" for new ones. Invalid fields show an alert icon, error text and an invalid border, associated through `aria-describedby` and `aria-invalid`. Duplicate destinations read `Already linked to "name". Choose another folder.` The selection dialog shows "N files · size · on the hub" and "Needs size · free" beside the destination check.

Files and synchronization stay the same."; the music icon names the dialog.

### Boundaries

The frontend never invents remote completion, TLS, available disk space, hardware details, category icons, remaining attempts, countdowns without source data, predicted version numbers or device metrics. No per-folder pause, automatic linking or promotion, remote installation or custom OS-notification buttons exist. Native tray, window, dialogs and notification delivery need installer and device checks; DOM tests, browser previews and JavaScript exports do not certify them.
