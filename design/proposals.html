Proposals

Purely visual ideas, drawn with the kit's own classes, only while they are proposals. A board is the proposal: there is no ROADMAP entry until the maintainer approves it.

Boards 01

UI-DESK-FILES-PAGING

One way to show more

Desktop

Why. Lists grow three different ways: the Files tab replaces its rows with First files and Next files, History appends with Load more, and the phone appends with Show more files and Load older versions; History also labels its placeholder rows Loading when nothing is cached yet. The proposal makes every list grow the same way, with one Show more button that appends the next rows (Show more files, Show more, Show more versions) and placeholder rows without a label. The alternative keeps page-by-page navigation on desktop and only renames the buttons.

Accept

Files, History and a file's history on desktop and web end in one Show more button (Show more files, Show more, Show more versions) that appends the next rows and keeps scroll and typed search, as DESK-FILES-PAGING describes; the phone's buttons use the same words; placeholder rows carry no Loading label; JSDOM tests cover the three lists and design/desktop.html shows a list ending in Show more.

UI-MOB-GALLERY-ALL-PHOTOS

All photos says what it uploads

Mobile

Why. Unticking the last album silently turns the choice into All photos, and saving then uploads the whole library without a word about it. The picker also offers Open settings for any error, not only a permission error. The proposal states what All photos uploads and how many items that is, and shows Open settings only when the phone refused access.

Accept

With no album ticked the All photos row carries the caption and the item count; Open settings appears only when the error is a permission refusal; the photo-uploads SPEC section and a mobile test cover both.

UI-SITE-PHONE-CTA

A phone visitor can reach the phone apps

Site

Why. At phone width the site's hero offers one primary action, Download for macOS, which a phone visitor cannot use, and the hero illustration's floating card can cover text. The proposal adds a plain link to the mobile section under the primary action at narrow widths and moves the card so no text is covered.

Accept

At 390 px the hero shows the text link to the Arca for mobile section under the primary action and its illustration card covers no text; a site test checks the link and its target anchor.

UI-DESK-TOUCH-TARGETS

Web admin on a phone has touchable buttons

Desktop and web

Why. The web interface opened on a phone keeps 28 to 32 px ghost and icon buttons, under the 44 px the phone app guarantees. The proposal raises them to the shared minimum touch target at 760 px and narrower, and only there.

Accept

At 760 px and narrower every ghost and icon button measures at least --touch-target-min; wider layouts are unchanged; a stylesheet contract test covers the media query.

Format 02

Board

One article per idea, tagged with its task ID. It carries the ID, the area (System, Desktop, Mobile), a title, why it is worth doing, a "Now" drawing of what exists, a "Proposed" drawing, and what proves it done.

Drawings

Both drawings use production and kit classes only, so the page reads as the app would. A drawing is never a screenshot and never introduces a colour or size outside the tokens.

Lifecycle

Idea: a board only. Approved: one ROADMAP Queue line of type ui with the board ID, whose accept is the board. Shipped: the board is deleted, the changelog and SPEC record it, and this kit is updated.

No visual part

Behaviour, data and infrastructure tasks live only in ROADMAP and never get a board.
