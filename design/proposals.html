Boards 01

UI-FOLDER-STATS

A folder summary that adds to its title

Desktop · Mobile

Why. The folder summary repeats the header: Files 24 · 196.3 KB indexed sits under a title that already says 24 files · 196.3 KB local, and Latest known revision shows an internal counter (rev 189886) nobody can act on. The phone has the same Files cell and keeps Last completed apart from Status. The proposal gives both platforms the same three cells: Status with when the last sync completed, Last change with when the newest accepted revision arrived, which file and which machine (the row both apps already read for Recent), and Revision history as it is. The alternative keeps four cells and only swaps the revision number for the file and machine, which still repeats the count.

Accept

Desktop, web and phone folder details show Status (with the last completed sync), Last change (the newest accepted revision's relative time, file and machine, or No changes yet) and Revision history, and no Files cell; the file count and size stay in the title; the hub's retention control keeps its cell; the phone reads the newest revision as FOLDER-LAST-CHANGE describes; JSDOM and layout tests cover both, and the kit pages show the summary.

UI-DESK-FILES-PAGING

One way to show more

Desktop

Why. Lists grow three different ways: the Files tab replaces its rows with First files and Next files, History appends with Load more, and the phone appends with Show more files and Load older revisions; History also labels its placeholder rows Loading when nothing is cached yet. The proposal makes every list grow the same way, with one Show more button that appends the next rows (Show more files, Show more, Show more revisions) and placeholder rows without a label. The alternative keeps page-by-page navigation on desktop and only renames the buttons.

Accept

Files, History and a file's history on desktop and web end in one Show more button (Show more files, Show more, Show more revisions) that appends the next rows and keeps scroll and typed search, as DESK-FILES-PAGING describes; the phone's buttons use the same words; placeholder rows carry no Loading label; JSDOM tests cover the three lists and design/desktop.html shows a list ending in Show more.

UI-DESK-FINDER-WORDS

Open and show in the Finder say different things

Desktop

Why. Open in Finder appears twice with two meanings and two placements: in a folder's header it opens the folder, in a file's detail it reveals the file and sits inside the ellipsis menu next to Rename… and Delete file…, while the header's own button is Open file. The proposal keeps the placements, which follow one rule (the header opens the content, the menu holds the rest), and uses the Finder's own word for revealing: Show in Finder on macOS, Show in folder elsewhere. The alternative surfaces the reveal action in the file header, which crowds it with a third button for something used far less than Open file.

Accept

The file detail's menu reads Show in Finder on macOS and Show in folder on Windows and Linux, the folder header keeps Open in Finder / Open folder, and no other wording changes; a JSDOM test covers both labels and design/desktop.html shows the file detail.

UI-DESK-RETENTION-PANEL

The retention control leaves the summary

Desktop

Why. On the hub, the Revision history cell of a folder's summary holds a compact segmented control (Off, 1d, 1w, 30d, Forever) among three read-only cells, with abbreviations the replica never shows and no room to say what the choice does. The proposal makes the summary read-only for both roles and gives the hub a Revision history panel in the side column, next to Path, Copies and Hub working copy, with the full labels and one sentence on the consequence. The alternative keeps the control in the cell and only lengthens its labels, which does not fit four cells.

Accept

The folder summary's Revision history cell is read-only on every role; on the hub the side column adds a Revision history panel with the segmented control (Off, 1 day, 1 week, 30 days, Forever), the same action and confirmation as today and a sentence stating the consequence; a JSDOM test covers both roles and design/desktop.html shows the hub's panel.

UI-DESK-CLEANUP-WORDS

Cleanup says what it removes

Desktop

Why. Settings offers Preview cleanup… under a row called Kept, with a second row called Limits that is not a setting but a safeguard; the dialog is titled History retention, asks for days and versions with the aside 0 disables, and its button reads Preview before it turns into Apply cleanup. The proposal names the action by what it does, Clean up…, moves the safeguard to one hint line, titles the dialog Clean up older revisions, phrases the two fields as a sentence, and shows the Would remove / Keeps count before Apply cleanup, which the dialog already computes. Nothing changes in what is protected. The alternative keeps the rows and only renames the button, which leaves the Limits row posing as a setting.

Accept

Settings → History shows one row, Older revisions, with Clean up… and a hint line stating the safeguard; the dialog is titled Clean up older revisions, phrases its two fields as drawn, previews the counts before enabling Apply cleanup and never removes anything before that; the same API and protections apply; a JSDOM test covers the copy and the two-step flow and design/desktop.html shows the dialog.

Format 02

Board

One article per idea, tagged with its task ID. It carries the ID, the area (System, Desktop, Mobile), a title, why it is worth doing, a "Now" drawing of what exists, a "Proposed" drawing, and what proves it done.

Drawings

Both drawings use production and kit classes only, so the page reads as the app would. A drawing is never a screenshot and never introduces a colour or size outside the tokens.

Lifecycle

Idea: a board only. Approved: one ROADMAP Queue line of type ui with the board ID, whose accept is the board. Shipped: the board is deleted, the changelog and SPEC record it, and this kit is updated.

No visual part

Behaviour, data and infrastructure tasks live only in ROADMAP and never get a board.
