Proposals

Purely visual ideas, drawn with the kit's own classes, only while they are proposals. A board is the proposal: there is no ROADMAP entry until the maintainer approves it.

Boards 01

UI-MOB-PAIR-ONE-FLOW

One pairing screen on the phone

Mobile

Why. The phone pairs through two different screens. Onboarding asks for the hub address, then the six-cell code, then the name, and says "Pair this phone". Devices, when the phone has no hub, asks for the name first, a plain monospace field for the code, a different address placeholder and says "Pair this device". Same task, two layouts, two wordings.

Accept

Devices without a hub renders the onboarding pairing step (address, six-cell code with its separator, name, "Pair this phone", placeholder https://arca.your-network); one component serves both places; the phone test covers both entry points.

Format 02

Board

One article per idea, tagged with its task ID. It carries the ID, the area (System, Desktop, Mobile), a title, why it is worth doing, a "Now" drawing of what exists, a "Proposed" drawing, and what proves it done.

Drawings

Both drawings use production and kit classes only, so the page reads as the app would. A drawing is never a screenshot and never introduces a colour or size outside the tokens.

Lifecycle

Idea: a board only. Approved: one ROADMAP Queue line of type ui with the board ID, whose accept is the board. Shipped: the board is deleted, the changelog and SPEC record it, and this kit is updated.

No visual part

Behaviour, data and infrastructure tasks live only in ROADMAP and never get a board.
