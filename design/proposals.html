Proposals

Purely visual ideas, drawn with the kit's own classes, only while they are proposals. A board is the proposal: there is no ROADMAP entry until the maintainer approves it.

Boards 01

UI-INFO-NOTICE

Default colour of info notices

System

Why. A decision drawn as a proposal. Info notices (saved, unlinked, copied) invert paper and ink today, the strongest surface in the app for its least important message. The proposal takes the primary green in both themes and keeps the shape, the four-second timing and the link. The alternative is to keep the inverted paper: no work, SPEC already documents it.

Accept

A yes or no on green. Yes: the info notice tokens (--notice-info-bg, --notice-info-fg, --notice-info-link) and their mobile counterparts take the green surface in light and dark, SPEC's Notices variants line is rewritten, a token test covers both themes and design/ is regenerated. No: this board is deleted and the inverted paper stays.

UI-WEB-REPLICA-DOWNLOAD

Download in a replica's web file detail

Desktop

Why. A product decision drawn as a proposal. A server replica's web administration cannot open a file on the machine, so its file detail offers nothing to do with the file itself, while the hub's shows Download file. The proposal adds the same secondary action, served from the replica's own complete local copy and never from the hub. The alternative is to leave a replica's file detail read-only, as today.

Accept

A yes or no on offering Download. Yes: a server replica's web file detail shows Download file for an available local file, served from its own copy with no hub request, and a JSDOM test covers it on a replica and on the hub. No: this board is deleted.

UI-DESK-SAVED-FILE-HISTORY

Offline file history without holes

Desktop

Why. Offline, a file's history is a union of saved windows, so a recent burst is followed by old revisions with nothing between them, and Restore still looks available. The proposal keeps only rows without holes, says so with the same hint the folder view uses, and disables Restore like the other hub-only actions. The alternative is to show every saved row with a divider where the gap is, which keeps more rows but still cannot restore.

Accept

Saved file history lists only rows without holes, its hint reads "recent entries only" like the folder view, and Restore is disabled with the hub-only reason while offline; a daemon test with a busy folder and a JSDOM test cover it, and design/desktop.html is updated.

UI-DESK-HUB-ONLY-MORE

Backup controls wait for the hub

Desktop

Why. On a replica with the hub unavailable, the backup switch and its Choose… picker look usable but call the hub and fail. The proposal disables them with the reason every other hub-only control already carries as its title, and enables them again on reconnection. The alternative is to also print the reason as a hint under the card, which is visible without hovering but adds a line to an already full screen.

Accept

On a desktop or server replica, Enable and Disable full backup and their Choose… picker are disabled with "Needs the hub, which is unavailable." while the hub is unavailable and follow reconnection like the other hub-only controls; a JSDOM test with the hubOnlyActions list covers it.

UI-ONB-DESK-FLOW

One step for name and role

Desktop

Why. The desktop and web wizard takes five pages on a first run (six on a server, which adds the access step): welcome, name, role, pairing and folder root. Name this machine is a page with one field, the role page is two cards that do not say who each role is for, and the rail lists four steps. The proposal puts the name and the role on one page, with a line on who each role is for, and shortens the rail to This machine, Connect and Folders; Connect reads Not needed for a hub. On a server the access page belongs to This machine. The pairing page, the folder page and the Finish page are as they are. The alternative is to keep the two pages and only add the guidance to the role page.

Accept

Name and role share one step on desktop, web and server onboarding, with a line on who each role is for; the rail reads This machine, Connect, Folders and marks Connect Not needed for a hub, and a server's access page sits under This machine; the pairing, folder and Finish pages, the durable onboarding state, the tentative browser values on a server and the hub skipping pairing are unchanged; JSDOM tests walk the hub, replica and server paths, and design/desktop.html shows the wizard.

UI-ONB-DESK-DISCOVERY

Hubs found nearby while pairing

Desktop

Why. Machines already lists the hubs Arca detects while a replica is disconnected, but the wizard asks for the address to be typed even when the hub is one tap away. The proposal lists detected hubs above the address field on the pairing step; choosing one fills the address, and the pairing code is still required, because discovery never links machines. With nothing detected the step looks as it does today. The alternative is a single Use detected hub link under the field, which takes less space but hides which hub it would fill in.

Accept

The pairing step of a replica, on desktop, web and server onboarding, lists the hubs the discovery read reports (name and address, never linking by itself) and choosing one fills the address; with no detected hub the step is unchanged and a discovery failure never blocks typing an address; a JSDOM test with a fake discovery covers a list, an empty read and a failed read, and design/desktop.html shows it.

UI-ONB-SERVER-ACCESS

The command for the server access code

Desktop

Why. On a Docker server the access step tells the person to run arca web-code and copy the code from the reply, while SPEC documents docker exec with the container name and the reply is JSON, so the first step of a server install is a guess. The proposal prints the command to run with a Copy button and says which field of the reply is the code. Umbrel keeps its own link to the app-password page. The alternative is to keep the sentence and add the command to the README only.

Accept

The web access step of an unconfigured Docker server shows the documented command with a Copy button and says the code is the code value of the JSON reply; Umbrel keeps its link; no code is ever shown or logged by the page; a JSDOM test covers both variants and design/desktop.html shows the step.

UI-ONB-MOB-WELCOME

Say where the hub comes from

Mobile

Why. A phone is never a hub, so the first person to install the app without a hub meets a wall: the welcome ends with You will need a hub and a pairing code, and nothing says where either comes from. The proposal replaces that caption with a card that says to install Arca on a computer or a server, make it the hub and open Machines → Pair a machine. It adds no control and no step. The alternative is a link to the install page, which needs a browser round trip and a public address that does not exist yet.

Accept

The mobile welcome shows the You need a hub first card with the copy drawn in place of the caption, in light and dark and in the Fold layout, with no new control or step; SPEC's mobile onboarding line, which says there are no welcome cards, is rewritten; a layout test covers it and design/mobile.html shows the welcome.

UI-ONB-MOB-PAIR

Pairing asks for what the hub shows, in its order

Mobile

Why. The pairing screen starts with the phone's name, which already has a default, and only then asks for the two things the person is carrying over from the hub, with no hint of where they come from. The proposal says on top that the hub's Machines → Pair a machine shows both, and orders the fields as the hub does: address, code, then the name, which keeps its default. The alternative is a QR code scanned from the hub, which removes typing but needs a camera module and a native build, so it is filed apart as an idea.

Accept

The mobile pairing step shows the sentence and the order drawn, keeps the same fields, validation and disabled state of Pair this phone, the expiry hint with its clock, the three progress dots and the name's default; a layout test covers the order and the sentence and design/mobile.html shows the step.

UI-MOB-THUMB-PROGRESS

Say that previews are being prepared

Mobile

Why. Opening a photo folder whose files are on the phone shows grey tiles with nothing saying whether previews are coming, how many are left or that some failed; a failed preview is dropped without a word. Uploads already have a row above the grid for the same kind of wait. The proposal adds one row in the same place while previews are prepared, with the count done of the photos on the phone, and a failure state with Retry. It leaves when the work is done. The alternative is a small counter in the folder header, which says less and has no place for Retry.

Accept

Opening a photo folder with photos on the phone shows the Preparing previews row above the grid with a done of total count while previews are prepared, replaced by the failure row with Retry when some could not be made, and absent when none are missing; layout tests cover the three states and design/mobile.html shows the row.

UI-MOB-CRASH-RECORD

A notice after a crash

Mobile

Why. After an uncaught error the app closes without a word and the next launch opens as if nothing had happened. The proposal shows one error notice on that launch, once, persistent until dismissed, with Details and Copy holding the recorded message so it can be reported; nothing is sent anywhere. The alternative is a warning notice with Dismiss only: shorter, but nothing to copy.

Accept

An uncaught JavaScript error on mobile is persisted and shown once, on the next launch, as the error notice drawn, with its recorded message under Details and Copy and never again after Dismiss; a test covers record and display and design/mobile.html shows the notice.

Format 02

Board

One article per idea, tagged with its task ID. It carries the ID, the area (System, Desktop, Mobile), a title, why it is worth doing, a "Now" drawing of what exists, a "Proposed" drawing, and what proves it done.

Drawings

Both drawings use production and kit classes only, so the page reads as the app would. A drawing is never a screenshot and never introduces a colour or size outside the tokens.

Lifecycle

Idea: a board only. Approved: one ROADMAP Queue line of type ui with the board ID, whose accept is the board. Shipped: the board is deleted, the changelog and SPEC record it, and this kit is updated.

No visual part

Behaviour, data and infrastructure tasks live only in ROADMAP and never get a board.
