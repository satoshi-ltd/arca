Proposals

Purely visual ideas, drawn with the kit's own classes, only while they are proposals. A board is the proposal: there is no ROADMAP entry until the maintainer approves it.

Boards 01

UI-INFO-NOTICE

Default colour of info notices

System

Why. A decision drawn as a proposal. Info notices (saved, unlinked, copied) invert paper and ink today, the strongest surface in the app for its least important message. The proposal takes the primary green in both themes and keeps the shape, the four-second timing and the link. The alternative is to keep the inverted paper: no work, SPEC already documents it.

Accept

A yes or no on green. Yes: the info notice tokens (--notice-info-bg, --notice-info-fg, --notice-info-link) and their mobile counterparts take the green surface in light and dark, SPEC's Notices variants line is rewritten, a token test covers both themes and design/ is regenerated. No: this board is deleted and the inverted paper stays.

UI-WEB-REPLICA-DOWNLOAD

Download in a replica's web file detail

Desktop

Why. A product decision drawn as a proposal. A server replica's web administration cannot open a file on the machine, so its file detail offers nothing to do with the file itself, while the hub's shows Download file. The proposal adds the same secondary action, served from the replica's own complete local copy and never from the hub. The alternative is to leave a replica's file detail read-only, as today.

Accept

A yes or no on offering Download. Yes: a server replica's web file detail shows Download file for an available local file, served from its own copy with no hub request, and a JSDOM test covers it on a replica and on the hub. No: this board is deleted.

UI-DESK-SAVED-FILE-HISTORY

Offline file history without holes

Desktop

Why. Offline, a file's history is a union of saved windows, so a recent burst is followed by old revisions with nothing between them, and Restore still looks available. The proposal keeps only rows without holes, says so with the same hint the folder view uses, and disables Restore like the other hub-only actions. The alternative is to show every saved row with a divider where the gap is, which keeps more rows but still cannot restore.

Accept

Saved file history lists only rows without holes, its hint reads "recent entries only" like the folder view, and Restore is disabled with the hub-only reason while offline; a daemon test with a busy folder and a JSDOM test cover it, and design/desktop.html is updated.

UI-DESK-HUB-ONLY-MORE

Backup controls wait for the hub

Desktop

Why. On a replica with the hub unavailable, the backup switch and its Choose… picker look usable but call the hub and fail. The proposal disables them with the reason every other hub-only control already carries as its title, and enables them again on reconnection. The alternative is to also print the reason as a hint under the card, which is visible without hovering but adds a line to an already full screen.

Accept

On a desktop or server replica, Enable and Disable full backup and their Choose… picker are disabled with "Needs the hub, which is unavailable." while the hub is unavailable and follow reconnection like the other hub-only controls; a JSDOM test with the hubOnlyActions list covers it.

Format 02

Board

One article per idea, tagged with its task ID. It carries the ID, the area (System, Desktop, Mobile), a title, why it is worth doing, a "Now" drawing of what exists, a "Proposed" drawing, and what proves it done.

Drawings

Both drawings use production and kit classes only, so the page reads as the app would. A drawing is never a screenshot and never introduces a colour or size outside the tokens.

Lifecycle

Idea: a board only. Approved: one ROADMAP Queue line of type ui with the board ID, whose accept is the board. Shipped: the board is deleted, the changelog and SPEC record it, and this kit is updated.

No visual part

Behaviour, data and infrastructure tasks live only in ROADMAP and never get a board.
